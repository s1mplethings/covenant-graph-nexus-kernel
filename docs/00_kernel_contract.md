# CGKN Kernel Contract

## False-Pass supervision and ProviderJob execution (normative)

The formal responsibility split is: Provider authors project design,
implementation, integration changes, and customer-project semantic repairs;
CGKN owns durable state, deterministic ProviderJob scheduling/routing/merge,
canonical verification, evidence, packaging, and the delivery gate; Codex is a
sparse independent False-Pass Auditor. This section supersedes any older
project-specific repair wording that conflicts with this split.

CGKN MUST NOT repair customer-project behavior using domain-specific kernel
code. Project generation and semantic repair belong to Provider. CGKN routes,
verifies, records, and gates. Generic environment setup and deterministic
validation may not synthesize project behavior, tests, screenshots, media, or
other evidence.

The production project-work unit is the minimal `ProviderJob` contract:
`id`, `goal`, `depends_on`, `owns`, `interfaces`, and `acceptance`. Provider
planning is an API responsibility. Dependency resolution, bounded concurrency,
ownership checks, PatchSet merge ordering, failed-job closure, and PASS-job
reuse are deterministic CGKN responsibilities. Workers operate on isolated
inputs and may return changes only for `owns`; shared files belong to an
integration job. One job may own multiple paths when they form one natural,
independently verifiable change unit with compatible dependencies and a bounded
combined output. `CGKN_PROVIDER_PARALLELISM` controls concurrency and defaults
to 4. A dependency cannot start before every dependency passes.

Codex assessment is read-only and is invoked only for high-value positive
transitions: requirement/acceptance freeze, integration complete, and proposed
final public delivery. Ordinary Provider leaves, API retries, test failures,
and negative checkpoints never invoke Codex. The auditor treats every CGKN
positive release verdict/status as an untrusted claim, seeks evidence-bound
counterexamples, and resumes when it cannot identify a concrete contradiction.
Canonical actions are only `resume`, `rework_project`, `recheck_evidence`,
`repair_kernel`, `user_decision`, and `halt`. A deterministic router sends
project issues to Provider, evidence/identity issues to canonical rechecking,
and actual CGKN defects to a separate governed kernel-repair execution.

The production bridge MUST consume the router receipt rather than convert a
non-resume audit into an ordinary Provider exception. `rework_project` writes a
bounded repair plan and resumes the existing production leaf executor for only
the affected jobs, then repeats Provider validation and the original audit.
`recheck_evidence` invokes no Provider: it invalidates the affected stale
canonical receipts, reruns their canonical producer/verifier, and repeats the
original audit. `repair_kernel` invokes the governed repair path, requires its
regression checks to pass, and repeats the original audit. `user_decision`
enters waiting-user-review and `halt` stops explicitly. The hard constant
`MAX_SUPERVISION_REWORK_ROUNDS=2` means that two consecutive audit refusals at
one recovery checkpoint produce `NEEDS_REWORK`; no recovery loop is unbounded.

`scripts/provider_jobs.py` is a pure ProviderJob/PatchSet contract and ownership
validator. It MUST NOT own a worker pool or scheduler. The dependency-wave,
bounded-concurrency split-file leaf executor in
`scripts/run_local_pipeline_impl.py` is the single production ProviderJob
execution authority, including same-run affected-only repair and PASS reuse.
Affected-only repair sends the exact current target source and evidence-bound
failure facts through that same leaf executor. Before any returned patch is
written, deterministic affected-behavior coherence checks must show the
targeted contradiction is gone and no new contradiction was introduced.
Validation and acceptance remain ProviderJob-scoped: one rejected peer job
cannot erase a separately verified job delta, and any accepted subset is
re-audited before another bounded repair round or release decision.

A valid product-shaped but ambiguous goal is not a user-decision blocker merely
because its technical stack, page layout, database, entity fields, status names,
workflow labels, or first-release scope are unspecified. The requirement lane
must infer coherent conservative v1 defaults, record those assumptions in the
frozen ProjectSpec, and set `ready_to_generate=true`. It may block autonomous
ProjectSpec creation only for contradictory requirements, a critical external
fact that cannot reasonably be inferred, required credentials or authority, a
high-risk or irreversible decision, or a choice the user explicitly reserved.

`ProviderJob` remains the natural ownership and validation unit; a bounded
Provider emission is only a transport detail inside that same stable job id.
Emission grouping uses expected source size, file type, file count, a
model-specific reliable output cap, and observed truncation without creating
synthetic project fragments or scheduler jobs. Each bounded emission requests
the already-computed effective reliable model cap so estimate variance does not
become an artificial truncation; grouping still uses the per-path estimates and
the reliable cap remains binding. Output truncated exactly at CGKN's requested cap
is a self-imposed insufficient request, not evidence of a lower model cap;
only truncation below the requested cap may lower the observed reliable limit.
Within the existing bounded retry budget, every rejected ownership-unit attempt
must feed its bounded validation error into the next Provider request. An
explicit self-imposed truncation may raise only that retry's output cap up to
the model's existing reliable ceiling; it cannot add a retry, scheduler, job,
timeout, ownership path, or alternate generation route. An incomplete emission
retains its validated `completed_owned_paths` and receives at most one completion call
for only its `missing_owned_paths`; CGKN never authors the missing customer code.
Every validated partial emission is durably checkpointed before the ownership
unit finishes. A missing co-owned path does not invalidate verified peer paths
unless an explicit manifest dependency makes the peer its consumer; resume and
the next bounded attempt request only the missing paths. The fixed generation
budget has a `MIN_COMPLETION_RESERVE` of 95 seconds measured against the original
hard deadline, which progress reporting cannot extend. Earlier emission chains
must stop at that reserve; once an ownership unit has verified partial output,
its last remaining bounded emission is the one prioritized completion and
ordinary retry cannot run ahead of it. Completion failure blocks the job and
cannot create fake materialization.
The foundation and component response boundary may strip a Markdown fence and
leading/trailing commentary around exactly one complete JSON object. Any other
malformed contract gets at most one Provider envelope-repair request, with no
field or source invention. Transport evidence records `requested_output_cap`,
`actual_output_tokens`, and `finish_reason`; attribution separately records
primary and fallback call counts, fallback execution/selection, and files
authored by each source.

Governed kernel repair runs outside the read-only assessment turn in an
allowlisted isolated mirror. It requires a reproduction check and regression
test target, may copy back only declared CGKN-owned source/test/doc/schema or
configuration files, rejects concurrent target changes, and must re-emit the
original checkpoint. It can never write `generated/`, `artifacts/`, `runs/`,
`workspaces/`, a customer candidate, or a delivery package; it also cannot
authorize formal evidence, packaging, delivery, or PASS.

Every run records `codex_supervisor_invocation_count`,
`codex_kernel_repair_invocation_count`, `provider_api_call_count`,
`provider_peak_concurrency`, `provider_jobs_total`, `provider_jobs_repaired`,
`provider_jobs_reused_after_pass`, `provider_owned_files_total`,
`provider_avg_files_per_job`, `provider_dag_wave_widths`,
`provider_dag_critical_path_waves`, `provider_fragmentation_ratio`, and
wall-clock stage timing as support metrics. These metrics cannot replace
canonical evidence.

## Candidate-first production lifecycle (normative)

The one production route is ordered `BUILD FIRST -> INGEST -> AUDIT -> REPAIR
-> RELEASE`. `BUILD_COMPLETE` is a workflow state meaning that the frozen
required file set is complete, paths and ownership are legal, and the bytes are
safe to save. It is never an EvidenceStatus, never means functionally correct,
and never authorizes packaging or delivery. `RELEASE_READY` is reached only
after every applicable canonical runtime, hidden acceptance, persistence,
integration, visual, package, identity, and positive Codex audit gate passes.

Only missing required paths, exhausted Provider generation, ownership
violations, unsaveable output, indeterminate candidate file sets, and explicit
permission or safety blockers are `BUILD_HARD`. User requirements, real public
APIs, and actual cross-component integration are `RELEASE_HARD`; Provider
implementation choices, internal symbols, style, and unused interfaces are
`ADVISORY`. A Provider manifest cannot promote its own declaration to
`BUILD_HARD`. Visual-design documentation added after the canonical project
plan is `RELEASE_HARD`: it remains mandatory before release but cannot prevent
the first immutable candidate from being ingested.

Once `BUILD_COMPLETE` is established, CGKN immediately records an immutable
provisional candidate with candidate id/hash, repository commit, ProjectSpec
hash, known issues, and Provider provenance. Repairs never rewrite a stored
version: an affected-only repair creates a child version bound to its parent and
issue ids. The mutable working projection is not candidate-version authority.
Every candidate must be closed over obvious local executable references before
materialization or versioning. Python local imports, declarative test-suite
parts, HTML script/stylesheet links, and local JavaScript module imports must
resolve inside the candidate unless they are external dependencies. A
BUILD-FIRST manifest projection must retain the transitive local dependencies
of every included entry. Recovery may promote only Provider emissions whose
paths are both canonically owned and successfully validated; an arbitrary
staging file cannot enter a candidate. Missing closure is `BUILD_HARD`, not a
reason to delete the reference, invent a test, or weaken delivery evidence.

Post-build evaluation collects every technically executable test, runtime,
browser, hidden-acceptance adapter, persistence restart, integration, visual,
contract, startup/README, and package-readiness result before Provider repair.
The canonical isolated customer-runtime probe recognizes both a root
`index.html` and the common `frontend/index.html` static-project entrypoint;
both are served from the clean copied project root and inspected at their
declared customer path before packaging. This recognition does not create a
second runtime or delivery route. Canonical pytest execution also pins
`--rootdir` and config discovery to the candidate project, so a candidate under
a repository artifact directory cannot inherit a parent repository's exclusion
rules and be falsely reported as zero tests collected. A pytest execution that
collects zero tests is always `FAIL`; only a successful non-pytest executable
probe may represent its one command as one passed check.
Generated tests may assert an exact project symbol identity only when the
symbol is explicitly backed by a public API, a cross-component frozen
interface, or acceptance. Provider-selected private helper names are
implementation detail and must be exercised indirectly through observable
behavior; renaming one without changing behavior cannot invalidate the suite.
It writes one issue ledger containing requirement, symptom, evidence, severity,
owner, affected ProviderJob, and repairability. Issues sharing a ProviderJob are
sent in one bounded repair request through that existing ownership unit; passed
unrelated jobs are reused. The existing bounded repair-round policy remains in
force. Diagnostic productivity metrics have no PASS authority.

Repair truth is ordered `hidden acceptance -> runtime/browser -> integration ->
ProjectSpec/user requirement -> internal validator`. The issue ledger must bind
each symptom to the exact user action, expected and observed behavior, evaluator
evidence, affected owned paths, and a root-cause key before routing. Symptoms
sharing a root cause or ProviderJob form one repair bundle. Each bundle receives
at most two Provider API calls through the existing split-file leaf executor;
non-target components and co-owned peer files are immutable source context, not
generation targets. Evidence contradictions rerun canonical evidence without a
Provider call. A Provider result is applied patch-first only to declared owned
targets; no actual source change is a failed attempt and cannot create a new
candidate version. Runtime test caches such as `__pycache__`, `.pytest_cache`,
and compiled Python bytecode are neither candidate source identity nor snapshot
content. All accepted bundle deltas are validated before one child
candidate is recorded, and the same evaluator is rerun against its new identity.
Provider transport diagnostics record redacted request identity/body size and
thread-local response-header/body timing without credentials. Fallback
observability distinguishes consideration, execution, and successful
selection; concurrency may be reduced for a local Provider only after an
actual fallback execution event, never from consideration alone.

This contract defines the stable kernel boundary for CovenantGraph Nexus Kernel. Future changes may add capabilities around the kernel, but they must not replace the generation mainline or bypass the safety and delivery boundaries described here.

## Kernel Responsibilities

CGKN Kernel is fixed responsible for:

1. Codex conversation entry for user project intake and generation confirmation.
2. `agent_session.jsonl` persistence for user messages, backend dialogue events, planner events, runner actions, and tool results.
3. `whiteboard` as the shared state surface for frontdesk, backend dialogue, planner agent, and generation agents.
4. `backend_dialogue_loop` as lightweight analysis and whiteboard update only; it is not a gate.
5. Running Codex conversation default project generation through API/provider project generation, provider output validation, post-build finalization, canonical evidence production, required user review, `local_packager`, public delivery gate, delivery receipt, active project binding, then canonical final verdict.
6. Keeping `pipeline_manifest`, `pipeline_planner_agent`, and `dynamic_pipeline_runner` as a support/experimental planning lane, not the Codex conversation default final project generator.
7. Using a CFO-controlled module plan inside `pipeline_manifest` when the support lane is explicitly used: the `cfo` role owns module planning, handoff order, acceptance interpretation, evidence review, and delivery readiness.
8. Allowing CFO support agents only inside the manifest as advisory context/risk maintainers, such as a context database and risk register. Support agents do not own Codex conversation default project generation, final route, implementation authority, or final delivery readiness.
9. Treating planning-only outputs such as `PRODUCT_PLAN.md`, `MODULE_PIPELINE.md`, `CFO_CONTEXT_DB.json`, `README.md`, or `TEST_REPORT.md` as planning/support artifacts unless provider project generation plus post-build finalization produces a runnable project surface and evidence.
10. Using `local_agent_actions` and `local_agent_skills` as the only tool execution boundary.
11. Using `local_packager.package_project` as the only formal delivery exit.
12. Treating the frozen, self-hashed canonical `delivery_manifest.json` as package evidence only after its inspector independently recomputes the current candidate/source hash, final ZIP hash, ZIP entry hash, evidence hashes, identity binding, and manifest/package delivery-directory binding. Canonical fields are reserved and cannot be replaced by extension metadata.
13. Allowing `dynamic_pipeline_runner` to recover complete actions from malformed or truncated agent JSON only inside the same manifest step, record the parse failure, and require a repair turn before that step can pass.
14. Allowing configured local models only as a model-source optimization. By default, local models may write public frontdesk/status replies only; generation-affecting local tasks such as customer classification, backend dialogue, planner, component generation/repair, CFO planning, context support, risk support, foundation, or QA must be explicitly enabled and must remain inside the same provider-output-validation/manifest/runner/evidence boundary. The Codex conversation service launcher may explicitly enable these reviewed tasks for a user-selected local-first deployment. Local component generation/repair must enter through the existing provider text call, produce parseable JSON, pass the same component ownership and output validation, and continue through post-build finalization, `local_packager`, and `public_delivery_gate`; it is not a second generation or delivery route. Invalid local output may fall through to the configured API provider but may never be promoted directly. When a local-model task is enabled, the router may auto-start the configured Ollama runtime (`CGNK_AUTO_START_OLLAMA`, enabled by default) before calling the model; this is runtime readiness only, not a generation route.
15. Recording critical setup questions for any explicitly required external, local, hosted, data, model, automation, security, storage, or runtime capability. These questions are shared context and acceptance constraints, not a new gate or generation route.
16. Recording a project-level capability strategy for core capabilities, advanced-method candidates, obvious route differences, and acceptance limits. This is universal planning context for the same manifest/runner flow, not a project-type-specific generator.
17. Wrapping Codex conversation user-facing narration in an action-based public expression layer. Public replies may describe what will be built, why input is needed, how testing works, what evidence will be shown, and how the user can continue or revise; this does not create a new formal generation path.
17. Requiring every formal `pipeline_manifest` to cover Product Studio evidence stages: `product_plan`, `technical_plan`, `build`, `test`, `review`, and `package`.
18. Auditing quality evidence before `package_project`, including `TEST_REPORT.md` and `DELIVERY_NOTES.md`, and recording missing evidence as warnings instead of hiding it.
19. Waiting for explicit user start confirmation when backend dialogue finds soft questions, critical questions, missing required inputs, or complex/high-uncertainty domains. These questions are not hard gates once the user explicitly starts; they become assumptions and delivery warnings.
20. Running public delivery gate before any final public delivery. The gate verifies canonical artifact schemas, hashes, run id, candidate hash, commit SHA, package integrity, and required attachment evidence. Missing required tests, runtime, previews, local models, datasets, or receipts produce canonical `NEEDS_REWORK` or a specific `BLOCKED_*` status.
21. Treating only `local_packager` final package output as the final delivery zip. `delivery_fact_check` records `any_zip_found` separately from `final_package_exists`; samples, fixtures, uploads, test data, and arbitrary `.zip` files must not satisfy final package delivery.
22. Sending only user-facing media/package artifacts by default in Codex conversation public delivery: `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`, `.mp4`, `.webm`, and `.zip`. Internal `.md`, `.json`, `.txt`, `.log`, manifest, report, and ledger artifacts stay inside the evidence bundle unless explicitly requested. Placeholder, mock, or fallback media cannot satisfy requested screenshots, backgrounds, sprites, generated images, or demo evidence.
22. Auditing build completion before a build step can pass. A worker build step must not report `pipeline_step_result.status=ok` unless it produced a real runnable project surface, including `app.py` or `main.py`, dependency metadata such as `requirements.txt` or `pyproject.toml`, source files, tests, and required visual evidence.
23. Auditing QA completion before a QA/test step can pass. If `TEST_REPORT.md` contains `NO TEST EXECUTED` or does not list real test commands, the step must be `rework_blocked`, not `ok`.
24. Treating Codex conversation `generation-mode=simulator` as preflight-only. It must record a recoverable blocked result and must never produce a public PASS, package, or delivery manifest.
25. Rejecting provider output locally when it is empty, unsafe, generic/template metadata, placeholder implementation, or missing `README.md`, `TEST_PLAN.md`, and a runnable entrypoint.
26. Preserving validated provider component PASS checkpoints across retryable transport failures. Failed attempts use separate diagnostics, while semantic repair invalidates stale component checkpoints once before regeneration.
26. Recording a deterministic delivery inclusion manifest in `delivery_manifest.json`, including POSIX relative paths, byte sizes, content hashes, and the final zip path. Formal `visual_required`, `media_required`, and `user_review_required` values come from workflow requirements rather than artifact presence. Local split-manifest normalization and formal manifest validation share the same component-id extraction and accept the bounded equivalent `component: {id, files}` wrapper while still enforcing the expected component id, required paths, and ownership. Source validation rejects explicit placeholder-implementation and TODO-comment claims but does not confuse functional placeholder attributes or the task status label `Todo` with unfinished work. Ollama code generation uses an explicit bounded prediction length and context window so a valid file request cannot run indefinitely; both remain environment-configurable within guarded limits. Component repair prompts preserve the selected requirement's persistence and integration contract and must not impose a fixed backend API or prohibit browser-local persistence. A native split frontend must contain a meaningful visible body, index generation must immediately enforce the exact split-manifest script/stylesheet paths, the merged frontend must resolve every local asset reference, task-board JavaScript must cover its explicitly requested behaviors, and generation must reject literal DOM references that are neither present in the HTML nor explicitly created by JavaScript. Browser module validation parses only actual static or dynamic `import` syntax; identifiers such as `importVideo` cannot be interpreted as package imports. Generated tests must inspect behavior in the file that owns it and cannot treat the Python `__main__` module guard as a function. An empty shell or structurally broken page must be repaired before browser screenshot or video evidence is accepted. Visual smoke uses actual non-empty DOM text, domain markers, browser errors, and decoded image evidence rather than an arbitrary long-text threshold, so concise valid interfaces are not classified as blank. `CGKNUserReviewRequest` binds `visual_required` explicitly in its self-hash; the request producer and inspector never infer it from screenshots, visual evidence files, presentation results, review files, or adaptive judgment. When true, the frozen request binds canonical test/runtime/visual evidence and a successfully sent, decoder-validated screenshot with the canonical screenshot hash; when false, visual evidence and screenshot roles cannot silently expand the review scope. Candidate-bound user review then requires Codex conversation update/message/date/from-user identity bound to the expected reviewer. The formal rule is that session booleans and text substrings are not review truth; neither are session request dictionaries or file presence. The review inspector independently checks request/ref hashes, visual scope, reviewer identity, timestamp order, evidence identity, presentation artifacts, and the durable replay ledger. Public-gate and send runtime state stays in session/truth-ledger records and must not mutate the frozen canonical manifest; the package path, ZIP hash, entries hash, and manifest artifact hash are rechecked immediately before the package document send.
   The formal Codex conversation evidence checkpoint sender re-inspects the frozen request and canonical visual evidence immediately before sending, permits only the canonical screenshot path/hash, treats only normalized successful Codex conversation returns as sent, and freezes optional Codex conversation message/chat metadata into the presented artifact. Exceptions, invalid returns, partial presentation, or pre-send changes produce `presentation_failed` before approval or packaging.
27. Never duplicating one sample image into screenshot, background, and sprite evidence, and never generating fallback media merely to satisfy a requested image capability.
28. Allowing only factual failures to force `BLOCKED`: missing project output, unsafe paths, missing claimed Codex conversation attachments, placeholder-only generation, or explicit provider failure. A final delivery without a packager zip cannot be `PASS`, but may remain available for user review. Codex conversation must not mark final delivery as delivered until the allowed public artifact set has actually been sent; final verdicts require the final package zip send to succeed.

`public_delivery_gate` remains a compatibility name for the wrapper that verifies canonical evidence, package integrity, and delivery receipts; it is not a second delivery route.

## Pipeline Module Mutation Contract

Replaceable support-lane modules may be changed only through reviewed repository changes that preserve their declared `contract()` boundary. This includes directly modifying, generating, or deleting bounded modules. truth modules—canonical evidence producers, inspectors, package and delivery gates—are not replaceable support modules and cannot be bypassed by a candidate bundle or module stub. A candidate bundle remains non-final until the canonical mainline independently validates and promotes it.

When the public delivery gate returns `rework_blocked`, Codex conversation session state must clear `generation.package_path`. A rejected or superseded package may remain on disk for diagnostics, but its path cannot remain advertised as a deliverable session artifact.

## Kernel Prohibitions

CGKN Kernel must not:

1. Reconnect the Codex conversation formal generation mainline to `generate_project.py`.
2. Reconnect the Codex conversation formal generation mainline to the raw `run_local_pipeline.py` CLI or any route that bypasses provider output validation, post-build finalization, `local_packager`, `delivery_fact_check`, or `agent_delivery_judgment`.
3. Restore `simulator` as the formal generation mainline.
4. Turn `backend_controls` back into an execution queue.
5. Treat `blocking_questions` or `soft_questions` as a hard gate for generation.
6. Allow `pipeline_manifest` to execute arbitrary Python.
7. Allow generation agents to modify CGKN kernel files.
8. Bypass `local_packager` or forge delivery completion.
9. Treat `agent_generated_pipeline` or CFO document outputs as Codex conversation default final project generation.
10. Count any fallback preview, placeholder, stub, procedural substitute, simulated result, or basic implementation as satisfying an explicitly requested core capability that requires a mature method, configured model, external API, local service, data source, automation engine, or runtime evidence.
11. Encode a project type, industry, object, or domain label as a special formal generation path. Domain labels may only help infer underlying capabilities; provider project generation remains universal.
12. Automatically start complex or under-specified project generation merely because soft questions are non-blocking. Non-blocking means the user may explicitly start with assumptions, not that the system starts by itself.
13. Treat internal reports, manifests, ledgers, or README-only folders as user-facing delivery results.

## Stable Flow

```text
Codex conversation
-> customer request
-> agent_session.jsonl
-> whiteboard / backend_dialogue_loop
-> API/provider project generation
-> provider response staging
-> canonical response -> decision -> patch -> production-candidate application
-> provider output validation
-> post_build_finalize
-> production-candidate provenance + provider causal trace
-> canonical test/runtime/visual evidence
-> user review when required
-> local_packager
-> public_delivery_gate
-> delivery_receipt
-> bind active project
-> final_verdict.json
```

The kernel is stable. The pipeline is agent-generated per project. The project itself is fully generated inside the bounded project directory. Skills are controlled capability modules. The whiteboard is the shared communication surface between intake, planning, generation, and delivery.

For generated projects with a visual surface, the same reviewed Provider route runs design discovery before component generation. `scripts/design_research_agent.py` searches multiple bounded reference classes, records source URLs and reuse boundaries, compares three visual directions, and selects one project-specific design contract. The generation-context librarian exposes only the bounded selected direction, design tokens, relevant references, and interaction/accessibility constraints to frontend, media, and design-document leaves. Provider output must include `docs/design_research.md` and `docs/design_system.md`, and component plus assembled-project validation rejects missing token reuse, responsive layout, keyboard focus, interaction feedback, reduced-motion behavior, source traceability, or selected-direction implementation. These are support planning and source-quality receipts only: they cannot replace canonical browser visual evidence, user review, packaging, or public delivery PASS, and they do not create another generation or delivery route.

## Consolidated Kernel Rule

CGKN Codex conversation default generation uses API/provider project generation as the formal project-file generator. The provider route must write real project files, validate provider output, run post-build finalization, produce canonical test/runtime/visual evidence, record required user review, package through `local_packager`, pass public delivery gate, record delivery receipts, and write the canonical final verdict before claiming completion.

Before canonical test/runtime/visual evidence, the formal provider route must freeze one `CGKNProductionCandidateProvenance` from `scripts.codex_conversation.start_generation_from_income -> run_provider_generation_job -> provider validation -> source-changing post-build`. It binds a unique run and candidate, the repository commit, the real customer candidate path, ordered self-hashed stage receipts, provider artifacts, and the independently reproducible candidate source manifest/hash. `scripts.production_candidate_provenance.inspect` must reread disk and recompute the manifest and candidate hash. Session/context booleans, `source_inspection="PASS"`, adaptive judgment, fixture output, acceptance output, and repository commit hashes cannot authorize this provenance. A provenance failure short-circuits canonical evidence inspection and adaptive delivery judgment.

Canonical source enumeration prunes the same root tool environments, caches, symlinks, and junctions that are excluded from the candidate hash before descending into them. Excluded dependency environments such as `.cgkn_test_env` cannot affect the hash and must not be recursively scanned during provenance or causal-trace inspection.

Canonical customer-runtime evidence stores at most the bounded observation body and hashes those exact stored bytes. It must not hash an unbounded pre-truncation response while recording only a truncated response, because the inspector must be able to reproduce every evidence hash from the persisted artifact.

The provider interface writes only to a run-unique response staging directory. `scripts.codex_conversation.py` is the sole formal `CGKNProviderCausalTrace` producer: before invoking the provider it freezes the request plus the production candidate's pre-provider manifest/hash; after return it refuses any out-of-band candidate mutation, freezes canonical response content, deterministically extracts implementation decisions, builds per-file hunks with byte-exact before/after content and hashes, applies those hunks to the production candidate, records the application receipt, binds any subsequent post-build source delta, and finally binds the same production provenance identity. A non-PASS Provider result must stop before response consumption and preserve its original blocker; it cannot be replaced by a missing-candidate or missing-staging causal-capture error. `scripts.provider_causal_trace.inspect` rereads every artifact and the candidate from disk, reconstructs response, decisions, hunks, patch application, post-build delta, source manifests and candidate hashes, and checks the ordered provider-generation, provider-validation and post-build receipts. Provider IDs, caller booleans, session state, adaptive judgment, acceptance output, and direct provider writes to the final candidate cannot substitute for this chain.

Provider component manifest prompts and validators must use the same canonical required-path authority. In particular, a browser-local static backend launcher may live at a canonical package path such as `app/main.py`; validation must not replace that frozen path with a hard-coded root `main.py` contract.

API/provider detection remains required operational support. The canonical persistent credential is the Windows User-level `CGKN_OPENAI_API_KEY`; it takes precedence over stale inherited process values, while the explicit one-run `CGKN_OPENAI_API_KEY_OVERRIDE` remains the only higher-priority override. Provider credentials must never be recovered from `.agent_private/NOTES.md`. Credential replacement must atomically set the canonical User value, clear User-level `CGNK_OPENAI_API_KEY` and `OPENAI_API_KEY` compatibility copies, scrub legacy note secrets, and report unresolved process or machine conflicts without logging their values. The CGKN plugin MCP manifest must pass the canonical `CGKN_OPENAI_API_KEY` and `CGKN_OPENAI_BASE_URL` process variables rather than requiring a cleared compatibility key, and both its guarded generation entry and direct diagnostic probe must use the canonical resolver while retaining process-level override and legacy compatibility resolution. The bounded probe requires explicit `RUN_PROVIDER_PROBE`, makes one minimal live request with the normal retry policy, classifies missing credentials, authentication, quota/permission, model, and transport failures, writes no candidate or delivery artifact, and always remains formal evidence `NOT_EVALUATED`. Its provider-compatible output floor is 128 Tokens; the bounded Alibaba Model Studio Qwen3.8 diagnostic request sets `reasoning.effort=none` so the probe observes a reply without spending its cap on reasoning. Alibaba Responses Qwen3.5 through Qwen3.8 component-file manifest and component-file generation requests also set `reasoning.effort=none`; this narrow transport policy is independently disableable, does not qualify `qwen-plus` or other model families, and does not change ProviderJob ownership, scheduling, validation, packaging, or delivery authority. Qualified Qwen3.8 component-file generation alone uses the separately contracted compact-leaf request envelope below, while other Provider generation payloads remain unchanged. `gpt-4.1-mini` smoke tests may call `https://api.gptsapi.net/v1/chat/completions`, and retryable provider transport errors such as `SSLError`, `SSLV3_ALERT_BAD_RECORD_MAC`, timeouts, connection resets, 502, 503, 504, or empty responses must be retried before declaring NEEDS_REWORK. Provider support must not write API keys to logs or project files, and must not create fake delivery assets after retry exhaustion.

Leaf implementation-depth validation distinguishes executable behavior from interface declarations. If `needs_direction_confirmation`, `soft_questions`, `critical_questions`, `missing_required_inputs`, a complex/high-uncertainty domain, or low confidence is present, intake records `generation_start_waiting` and waits. If the user explicitly says to start, unanswered questions and missing inputs are written into `generation_context_snapshot` as assumptions and warnings; outputs with missing real inputs must be partial/scaffold evidence, not full validation.

Capability strategy fields such as `capability_strategy` and `capability_research_targets` guide CFO planning and support agents for every project. They must describe underlying capabilities and advanced-method candidates, not project-type-specific branches. They do not authorize legacy pipelines, arbitrary execution, or bypassing manifest validation.

Public narration is allowed only at Codex conversation reply boundaries. It may redact internal terms and present progress through concrete actions and evidence, but the underlying Codex conversation default execution remains `api/provider project generation -> provider validation -> post_build_finalize -> canonical evidence -> required user review -> local_packager -> public_delivery_gate -> delivery_receipt -> bind active project -> final_verdict.json`.

Fallback to a single agent loop is allowed only when pipeline planning or runner execution fails, and it must record `pipeline_fallback`.

Cross-file Python callable mismatch feedback includes the authoritative expected signature so repair does not have to infer positional, keyword-only, variadic, or required parameters. Uniform stage-leaf prompts also require every return branch to directly yield a literal result mapping with a literal `success` or `error` status and a mapping output. Orchestrator repair publishes the exact statically inspectable `result = stage(state)` loop shape and result-field reads. Application-entry repair feedback publishes the exact required stage-list expression and requires a literal list or tuple so the executable graph remains statically inspectable. HTML expected symbols are translated into exact visible literal `id` contracts, while CSS `--*` expected symbols become exact `:root` custom-property contracts; language-specific publication meaning is never left for a Provider to guess. A Provider-authored JavaScript `expected_symbols` list describes implementation bindings only and cannot create a hard ES-export requirement by itself. JavaScript hard exports are the union of symbols actually imported by another generated module and symbols independently declared by the ProjectSpec or acceptance authority through `public_api_symbols_by_path` or `acceptance_required_symbols_by_path`; internal or unconsumed names remain manifest description. The deterministic gate checks browser loading semantics and rejects ES import/export syntax or a hard ES-export contract when the referenced source is loaded by a classic script rather than `type="module"`. Capability behavior, actual consumers, runtime coherence, and then authoritative implementation interfaces are evaluated separately so a Provider cannot expand project requirements by writing its own manifest. HTML ids, CSS tokens, authoritative JavaScript exports, local module imports, and unimported sibling calls are checked at each leaf boundary rather than deferred to whole-component review. Frontend CSS generation receives the same measurable design-system signals used by the final quality gate: eight or more tokens, a responsive focal composition, visible focus treatment, and reduced-motion handling. A high-complexity JavaScript product leaf with at least three published symbols is deterministically split into bounded symbol-owner modules plus its compatibility facade even when it falls below the general six-symbol expansion threshold. Bounded JavaScript symbol owners receive both nonblank-line and source-character ceilings in their initial prompts and validation receipts; any remaining unsplit high-complexity JavaScript leaf is bounded the same way so it cannot consume the entire Provider token allowance before validation. On an outer component retry, the formal route reloads the latest pending leaf target before computing the repair closure, preserving newly completed prefix checkpoints instead of replaying a stale earlier leaf. Larger responsibility sets must therefore become manifest submodules rather than a larger context window. These are generic leaf-repair rules and cannot become project-specific compatibility patches.

## Legacy Code Policy

Legacy provider pipeline code must not bypass post-build finalization, `local_packager`, or public delivery gate.

Legacy CLI may exist only under `legacy/` or as a thin wrapper.

Codex conversation formal generation may call the reviewed API/provider project generation implementation restored from the old provider chain, but it must not bypass post-build finalization, `local_packager`, or public delivery gate. `generate_project.py` and `simulator` remain disallowed as Codex conversation mainline.

### Pending leaf completion

The CGKN Codex plugin automatically selects the existing formal `--resume-run-dir` argument only when the project has a readable pending component-file or semantic-repair checkpoint whose raw user goal exactly matches the requested goal. Missing, malformed, completed, unsupported-stage, and goal-mismatched checkpoints continue as fresh reviewed runs; the plugin does not create a second generation or delivery path.

When the exact leaf named by a pending component-file repair passes its boundary and publishes its interface, CGKN immediately archives that pending target as completed. A later interruption therefore cannot keep invalidating an already repaired leaf while another downstream leaf is being generated; any later exhausted failure writes its own new exact pending target. Once a leaf exhausts its bounded repair attempts, that exhaustion is non-retryable at both the component transport loop and the outer semantic-generation loop; accepted sibling checkpoints remain reusable, but the same leaf cannot silently receive a fresh attempt budget. Python component-level publication checks follow Python module binding semantics: top-level `import` and `from ... import ...` names count as published interfaces, so a validated compatibility facade is not falsely rejected after its leaf boundary accepts the same exact re-exports. Within `tests/test_*.py` only, `test_*` methods directly owned by a top-level test class also satisfy test-manifest symbols because unittest and pytest collect them; product modules retain module-level publication rules. Required Python test manifests are normalized to explicit existing upstream providers before leaf graph construction: pipeline/integration tests bind stages and orchestrator, artifact tests bind the artifact store, cancel/resume tests bind the orchestrator, degraded-mode tests bind adapters, and application tests bind the real entrypoint. Only paths already present in the prior manifest may be selected; this feeds exact APIs through the librarian instead of letting tests invent undeclared modules. Python leaves with no declared local dependencies receive an explicit empty local-import contract: librarian excerpts remain contextual evidence and cannot authorize imports. Design-document traceability blockers always publish the exact required design-document paths as affected files, so missing source URLs, selected-direction naming, or anti-copying boundaries regenerate those documentation leaves instead of causing a cache-only component retry loop. Each regenerated design-document leaf receives a highest-precedence documentation contract from the bounded design-research context: it must reproduce the exact selected-direction name, cite at least three supplied source URLs, and include the canonical anti-copying boundary without paraphrase. This keeps source discovery in the librarian while making the leaf's quality obligations deterministic. The semantic repair compiler deduplicates identical blockers before planning. Any structured blocker carrying file evidence keeps those paths through the generic route, maps each path to its canonical component owner, and generates file-level actions; it may widen to a component only when no usable file evidence exists. Pending semantic repairs retain their parsed structured blockers on resume, including file hints and ownership evidence, instead of recompiling from lossy message strings. Artifact-store and artifact-contract leaves receive the exact required record fields and stage-artifact names from the frozen complexity contract as a highest-precedence schema contract. Their leaf boundary rejects omitted field/artifact names, opaque-byte stores, dummy or placeholder behavior, and pass-only documentation examples before those files can enter a component checkpoint. Code must validate structured records, and documentation must describe concrete producers, consumers, validation, and failure semantics.

When the frozen complexity contract requires both background and sprite generation, manifest normalization enriches the existing Provider component route rather than creating another path. `backend/image_adapters.py` must expose an executable deterministic offline PNG generator plus an adapter boundary and owns the concrete PNG write; `scripts/capture_workflow.py` must expose separate background and sprite workflows with prompt/seed/hash/type/path metadata, invoke those exact generator methods, then verify the returned path exists, read its bytes, validate the PNG signature, and compute the recorded hash before returning success; `demo/run_fixture.py` must generate at least two of each and verify PNG validity, hash diversity, and sprite alpha. The fixture receives the exact required stage-artifact names as a literal `REQUIRED_STAGE_ARTIFACTS` contract, executes the published application graph once through `main.initialize_app`, and must iterate, load, and validate every named JSON artifact without directly reconstructing `ProjectOrchestrator` or inventing private dependency helpers. This keeps orchestration in the application entry while the fixture owns runtime evidence materialization. This writer/verification ownership split prevents duplicate rendering in wrappers while keeping path-only success impossible. Capture validation is based on written-byte evidence rather than requiring the wrapper to rewrite a caller-selected filename or merely contain a `.png` token. Their leaf boundaries reject simulated-text success, fake bytes, missing adapter PNG writes, missing capture read-back checks, missing paths, and missing fixture evidence. The assembled-project deterministic complexity gate independently checks all three exact paths and routes any missing capability back to its owning leaf, including an inadequate upstream image adapter even when a semantic reviewer reports only a media symptom. If generated code imports `PIL`, the foundation dependency leaf and assembled-project gate require the `Pillow` distribution in `requirements.txt`; imports and install metadata cannot diverge. Optional external image providers may be unavailable only through honest degraded/error state; the offline default remains executable.

Both the leaf boundary and the assembled-project complexity gate enforce that ownership split consistently: the adapter must contain the concrete PNG write, while the capture wrapper must prove file existence, read the returned bytes, validate the PNG signature, and hash those exact bytes. The wrapper is never required to contain its own save/write call or a filename literal, and byte read-back without signature validation is still rejected.

The bounded capture-wrapper contract publishes the exact eight-byte PNG signature and the required `bytes.startswith(PNG_SIGNATURE)` rejection shape. This is a language-level interface invariant, not generated project content: it gives small models an unambiguous verification protocol while their returned wrapper source still comes from the reviewed Provider call and must pass the same leaf boundary.

The generated fixture contract likewise publishes a syntactically exact public import block (`hashlib`, `json`, `Path`, `initialize_app`, and both capture functions), requires every called helper to be defined before use, and recommends direct `Path.write_text(json.dumps(...))` artifact writing without f-string construction. These are bounded interface and syntax constraints; the Provider still owns the complete fixture implementation and its returned file must pass undefined-name, syntax, artifact, media, and runtime checks.

Generated pytest leaves treat fixture functions as dependency-injected values, never as the second `pytest.mark.parametrize` argument. The leaf AST boundary rejects a declared fixture referenced directly as `argvalues` and directs the same Provider leaf to request the fixture as a test parameter or supply a real iterable of cases. Generated media fixtures must decode PNG files before reasoning about pixels: transparency checks use Pillow RGBA alpha-channel extrema or pixels, and the leaf boundary rejects integer subscripting of variables populated by `Path.read_bytes()`. Compressed PNG offsets are container bytes, not decoded pixel evidence.

The media-fixture source boundary also requires decoded alpha-channel extrema with evidence that the minimum alpha is below 255; asserting equality to 255 proves opacity, not transparency. The fixture must contain a concrete structured-JSON write operation for required stage artifacts before it reads them back. These checks run during initial leaf generation and post-build repair, ahead of runtime evidence collection.

The bounded post-build fixture prompt publishes the exact evidence-write shape for small models: create parent directories, build a receipt derived from the application startup result with all frozen artifact fields, then call `artifact_path.write_text(json.dumps(receipt), encoding='utf-8')` before read-back. This specifies the interface protocol without supplying project-specific fixture content.

The fixture source boundary verifies that ordering as well as token presence: an artifact read-back or missing-file precondition placed before the structured receipt write is rejected. This prevents a superficially compliant but unreachable write from passing static validation and failing immediately at runtime.

For post-build repair, the same protocol is supplied as a named `required_stage_artifact_write_shape` that replaces the entire existing artifact loop. It explicitly forbids preserving a pre-write existence check, `FileNotFoundError`, or JSON read. Publishing a bounded generic control-flow scaffold is an interface constraint for small code models, not a project-specific generated-file patch.

The same two boundaries are reapplied to post-build file repair responses before any replacement is written. The repair prompt carries the pytest injection rule and decoded-image alpha rule whenever their target types are present, so runtime repair cannot bypass a constraint enforced during initial leaf generation.

Post-build Provider replacements use a bounded per-leaf output-validation retry loop. Every failed target file is requested, regenerated, and validated independently with its own accumulated boundary errors; this preserves the small-module generation contract even when one post-build run exposes several roots. No replacement is written until every requested leaf has passed, so the repair set remains atomic. A response omitting its one requested target or returning any additional file is rejected. Only a complete repair set that passes path ownership, syntax, pytest-fixture, media-decoding, and delivery-claim boundaries is written to the candidate.

Every Python post-build replacement also passes the same undefined-name analysis used by initial leaf generation. A replacement that calls an unimported library symbol, drops a dependency import, or otherwise leaves an unresolved name is rejected before it can overwrite the candidate and receives that exact name in its leaf-level retry feedback.

Post-build command diagnostics retain a bounded 12,000-character tail by default (configurable with `CGNK_POST_BUILD_COMMAND_OUTPUT_CHARS`, hard-capped at 20,000). This is large enough to preserve pytest traceback causes and the final failure summary together; a short summary-only tail cannot drive model-owned test repair. Diagnostic expansion does not change test status or substitute for the full on-disk stdout/stderr evidence.

The repair compiler then derives a bounded target-specific diagnostic excerpt for every requested leaf. A fixture leaf receives the structured fixture receipt and command traceback; a test leaf receives the pytest output window around its exact path; other leaves receive the global post-build window around their path. Per-leaf Provider requests carry that focused excerpt separately from the short global summary, so one verbose failure class cannot evict another target's root cause.

Provider test manifests cannot transfer production-interface names into test-leaf ownership. For Python files under `tests/`, normalization retains only exact `test_*` identifiers in `expected_symbols`; names such as a production `Stage`, parser, adapter, or orchestrator must be imported through the declared upstream dependency interface and exercised, never redefined inside the test merely to satisfy a symbol counter. Test responsibilities and acceptance checks remain intact, so removing false ownership does not weaken behavior or depth validation.

When a completed component-file repair is stored inside a semantic-repair wrapper, pending-leaf archival must unwrap the nested `repair_plan`, match the exact component and target, mark both records completed, and remove the active pending file before downstream work. A restart cannot force-regenerate an already validated leaf merely because the pending record was wrapped.

Leaf generation concurrency follows the active provider owner. When `component_generation` is assigned to the local model, the default is one leaf worker (optionally bounded to two with `CGNK_LOCAL_PROVIDER_LEAF_MAX_WORKERS`) so a single Ollama runtime is not flooded by external-provider concurrency assumptions. API-owned generation keeps the existing `CGKN_PROVIDER_LEAF_MAX_WORKERS` default of three. Validation, checkpoints, and repair semantics are identical under either scheduler.

When an API-owned run records `pipeline_fallback` to the local component-generation model, subsequent leaf batches use the same local one-worker scheduler for that run. The nominal API owner cannot keep three external-provider workers after the actual transport has moved to one Ollama runtime.

Component-manifest timeout caps also follow the active provider owner. API-owned planning remains hard-capped at 120 seconds. Locally owned component generation may be configured up to 240 seconds with `CGNK_PROVIDER_COMPONENT_MANIFEST_TIMEOUT_CAP`, because bounded librarian prefill plus a multi-file documentation manifest can exceed the API-oriented transport window on local hardware. Both the manifest call and its enclosing component/semantic-attempt call use this same owner-aware cap; an outer API-oriented limit cannot silently truncate the local allowance. The overall run deadline and manifest validators remain authoritative.

The local-model transport applies the same ownership distinction at its final request boundary. Generation tasks may run for up to 240 seconds (optionally lowered with `CGNK_LOCAL_MODEL_REQUEST_TIMEOUT_CAP`), while public-reply and other non-generation tasks remain capped at 120 seconds. Component-file generation and locally owned semantic review default to 180 seconds and may be adjusted through `CGNK_PROVIDER_COMPONENT_FILE_TIMEOUT_CAP` and `CGNK_PROVIDER_SEMANTIC_REVIEW_TIMEOUT_CAP`; API-owned calls retain their 90-second caps. Manifest, leaf, review, outer-attempt, and transport layers resolve the active owner before applying a cap. No downstream layer may reapply an unconditional API-oriented 90- or 120-second clamp after the pipeline has granted a longer bounded local-generation timeout.

For a backend with a frozen stage graph, manifest normalization also supplies canonical dependency edges before the leaf work graph and librarian query are built. The application entrypoint depends on the orchestrator; the orchestrator depends on the stage facade and artifact store; persistence and preview depend on the story/asset domain; and bounded stage children depend only on the domain modules they consume. These edges determine generation order, exact interface feedforward, downstream repair closure, and allowed imports. Semantic similarity alone cannot substitute for a declared dependency.

The normalized backend entrypoint publishes `initialize_app`, imports the frozen stage facade, constructs `ProjectOrchestrator` with every required stage in declared order, and executes that nonempty real graph. The normalized orchestrator consumes plain stage callables through `stage(state)` with a structured `status`/`output` result and must inspect both result fields rather than treating any arbitrary mapping as success. Every assigned frozen pipeline-stage function accepts exactly one `state` mapping and every return path emits a result mapping whose status is `success` or `error` and whose output is itself a mapping; returning the mutable input state or a string payload is rejected. These AST rules run both on a newly generated leaf and on current manifest-aware component-cache validation, so historical syntax-only PASS cannot preserve an empty graph or incompatible stage protocol. Structured artifact-store cache validation likewise rejects missing frozen record fields and opaque `Dict[str, bytes]` storage. Orchestrator validation rejects `stage.execute(state)` object-method assumptions, fixture validation rejects a defined `run_fixture` that is never executed from a main guard, and foundation validation parses generated `pyproject.toml` as TOML before it can enter a checkpoint. Cached-component and assembled-project quality validation repeat that TOML parse so a stronger current contract invalidates a stale malformed foundation checkpoint even when it is upstream of the active repair leaf. Component reasoning repair remains on the existing Provider generation route but is a code task and therefore uses the configured code model rather than the general reasoning model. Post-build diagnostics recognize TOML paths and configuration-syntax failures as foundation targets instead of misrouting them to frontend files. Deterministic leaf contract mismatches are bounded repairable generation failures: their complete rejection history is returned to the responsible leaf model within the existing Provider route instead of terminating after the first structurally valid but contract-invalid candidate. During semantic repair, spec-hash mismatch may be ignored only for components strictly upstream of the earliest repair target. Downstream checkpoints must match the current feedforward interface hash, so an upstream interface change invalidates stale tests/media/docs instead of retaining component PASS from an obsolete API.

A same-run semantic repair plan always overwrites empty or stale compiled identity fields with the exact live user goal and component pipeline before the next attempt. This identity is evaluated before requesting any component manifest: validated components strictly upstream of the earliest repair target are reused directly, while the target and affected downstream closure remain eligible for regeneration. A blank legacy `raw_user_goal` cannot silently turn an affected-only media repair into nondeterministic backend manifest regeneration.

For a generated project with `demo/run_fixture.py`, required pipeline artifacts, or the background/sprite stage pair, candidate post-build must execute the generated fixture through the bounded Python command runner. It independently verifies command success, rejects a structured failure result printed by a zero-exit fixture, verifies every declared stage artifact as parseable object JSON with the declared fields, requires at least four decoder-valid distinct PNG hashes when visual generation is required, and requires at least two sprite PNGs with meaningful transparency. Generated fixture media is validated by role: backgrounds retain the 640x360 minimum used for reviewable scene media, while named sprite/character assets use a 256x256 minimum plus the transparency contract; the screenshot geometry threshold must not reject valid square sprites. Fixture failure blocks screenshot collection, candidate review readiness, and post-build PASS; support receipts cannot substitute for the required project files. The post-build repair compiler includes the structured fixture receipt in its failure log and routes fixture or stage-artifact failures first to `demo/run_fixture.py`, exact traceback-named stage leaves, and the real media/stage owners, never to an unrelated frontend leaf merely because screenshot collection was subsequently blocked. Ordinary repairs remain capped at three exact files; a multi-root fixture/media failure may carry at most five evidenced owner files so distinct stage and image-generation defects are not repeatedly hidden behind the same generic three-file prefix. Deterministic-only repair suppression applies only when no model-owned test, fixture, stage-artifact, media, or runtime failure is present; a simultaneous deterministic frontend symptom cannot erase the model repair actions for those independent root causes.

When a generated Python test is repaired after post-build failure, the repair payload must include bounded exact definitions for the local functions, classes, and constants imported by that test, following facade re-exports to their implementation leaves. This dependency context is authoritative: repaired tests must call the implemented signatures and validate the implemented public result shape instead of inventing compatibility fixtures, methods, or legacy interfaces.

For a frozen `direct_cli_application`, post-build repair reloads the same named-package leaf contract from the pending reviewed component pipeline and attaches it to the exact implementation or split pytest target. The repair boundary reapplies the model/repository/service/CLI ownership and executable API rules before accepting a replacement: repository saves reject duplicate identifiers before storage replacement; service IDs stay strings, created timestamps stay JSON-safe strings, merge conflicts are not silently skipped, summaries keep their exact counters; every successful CLI command emits JSON; and pytest leaves cannot define global `tmp_path`, shadow imported runtime names with `None`, call unrequested fixtures, prepend a console program name to `main(argv)`, or pass an in-memory collection where the real API requires an import path. A syntactically valid unchanged leaf that preserves the observed runtime contradiction therefore remains rejected. This is the original Provider post-build lane consuming its frozen interface contract, not a new generator or deterministic project patch.

The direct-CLI foundation contract also freezes valid PEP 621 project metadata: `[project]` declares `requires-python = ">=3.11"` and an empty runtime dependency list, `[project.scripts]` maps the named command to the package CLI `main`, and `[build-system]` uses the exact `build-backend` key. Local split-file validation parses the TOML and rejects Poetry-only or misspelled substitutes, a missing Python requirement, runtime dependencies, or an absent console entry before the foundation checkpoint can be reused.

When API quota fallback produces an otherwise valid direct-CLI `pyproject.toml` but misses one of those exact metadata fields, the same bounded leaf route may use one additional local correction turn controlled by `CGNK_LOCAL_DIRECT_CLI_CONFIG_FALLBACK_ATTEMPTS` and capped at two total attempts. The correction explicitly restates the minimal PEP 621 fields, including the literal empty dependency list; it returns through the same strict one-file output and TOML validation contract and cannot write configuration deterministically or expand file ownership. Direct-CLI configuration anchors are executable TOML tokens (`requires-python`, `dependencies`, `project.scripts`, and `build-backend`), never natural-language descriptions, so a valid declaration cannot fail implementation-depth review merely because it does not contain prose such as "Python version requirement".

Candidate UI smoke validation derives its domain identity keywords from the current `complexity_project_contract.json` selected project name and summary, compares them case-insensitively, and never applies a fixed sample-domain vocabulary to unrelated generated projects. If no selected-project contract vocabulary exists, title, body length, console, network, and image checks remain authoritative without manufacturing a domain-keyword failure.

Candidate post-build may reuse an existing workflow video only after the canonical video diagnostic confirms that the file is non-placeholder, large enough, and longer than one second. A later usage-planning pass that produces no new video must not erase earlier valid evidence. Static HTML usage inventory follows the local CSS and JavaScript paths actually declared by `index.html`, including `src/` layouts, instead of assuming root-level sample filenames.

For a selected project with four or more user-visible pipeline capabilities, browser evidence must prove a real workspace rather than a titled shell: at least sixty percent of the required capability groups must be visible, the page must expose a bounded minimum of semantic interactive controls, at least three workspace regions, and sufficient visible product text. Browser capture records these structural metrics and post-build cannot pass or request user review when the UI quality smoke fails. UI repair is routed together to the existing HTML, JavaScript, and CSS owners with bounded sibling feedforward context so visible capability, behavior, and styling contracts remain aligned.

The same UI acceptance contract is enforced before repaired frontend source is written: HTML must expose the required capability coverage, semantic controls, regions, and visible text; JavaScript must bind several concrete controls to observable behavior without placeholder simulations; CSS must provide a substantial responsive multi-region layout. UI diagnostics are isolated from already-passing test and fixture logs, and each provider call carries its exact target path so local model routing and evidence remain attributable.

A workspace region may use a semantic section/article/aside, an explicit region/tab panel role, or a clearly named `.section`, `.panel`, or `.workspace-region` container. Complex frontend repair still must preserve modular ownership: `index.html` loads `src/styles.css` and `src/app.js`, while non-empty inline style/script blocks and visible unimplemented/TODO behavior are rejected.

When a repaired complex `index.html` already declares the required external owners, the source boundary deterministically removes non-`src` inline script and style blocks before validation. This ownership normalization never creates labels, controls, regions, styling, or behavior; the provider must still supply those product-specific elements and both external owner leaves must independently pass their contracts.

Frontend repair payloads compile the failed capability groups into a small `ui_repair_brief` with required visible labels, three product-specific feature areas, and exact structural minima. A repair may not return the existing shell unchanged or satisfy feedback by appending comments/duplicate selectors; HTML, behavior, and styling must replace the shell coherently.

For a `ui_quality_failure`, each frontend repair leaf discards its old shell content and is regenerated only from the exact UI contract plus already-accepted sibling replacements. The old HTML/JavaScript/CSS siblings are not repeated as repair context, preventing small models from copying a minimal shell. JavaScript self-imports are rejected before any atomic write.

When a frontend replacement fails its source boundary, the next bounded retry receives the ownership-normalized rejected replacement, the current unresolved validation error, and a bounded diagnostic history. It repairs the new source in place and preserves already-satisfied UI behaviors instead of restarting from the older candidate shell. If two normalized replacements are identical, the final bounded retry discards the stagnant source and regenerates only that leaf from the same UI contract and accepted siblings. The project tree remains unchanged until the complete repair set passes atomically.

The run librarian may retrieve candidate-only rejected leaves from the same run as bounded repair memory. It revalidates each bounded candidate against the current contract and selects the one with the fewest current violations, using source size and recency only as tie-breakers, instead of trusting the newest file or a stale historical error. The evidence remains rejected until current per-leaf and cross-owner checks pass, and even then it cannot be written or promoted without the complete atomic repair set. For HTML identity failures, the repair brief derives an exact visible body identity line from the bounded domain vocabulary and states that document-title or attribute text does not satisfy it.

Source-boundary feedback must be executable rather than qualitative. In particular, CSS repair feedback reports the observed concrete-rule count and the exact minimum, identifies a missing responsive breakpoint, and names the accepted grid/flex layout declarations. The UI repair brief carries the same measurable thresholds so a bounded local model can close the gap without guessing or repeated comment-only edits.

Frontend source and browser acceptance use the same visible-body and workspace-region semantics: document-head text cannot satisfy body-content thresholds, and semantic region elements or explicit `.section`, `.panel`, and `.workspace-region` containers are counted consistently. The selected contract's bounded domain keywords are carried into repair prompts and evidence. Inline event attributes, `not implemented`/`implement logic` prose, sample empty-state comments, console logging used as product behavior, and export-only DOM mutations cannot satisfy modular JavaScript behavior.

Complex workspace review includes a design-system and cross-owner interface gate. HTML provides one visible product header, hierarchical feature headings, an observable status region, and capability-driven real media preview slots. JavaScript binds DOMContentLoaded to the document, resolves accepted HTML ids/actions, and exposes more than export-only DOM updates. CSS must style the exact accepted workspace owner, define and consume a bounded token system, provide responsive grid/flex layout, hierarchy, radius/elevation, and keyboard focus treatment. The rule threshold is deliberately small and semantic requirements carry the quality weight, so duplicate selectors cannot substitute for design. A structurally populated screenshot whose blank score exceeds 0.90 remains a UI quality failure and cannot authorize review or delivery.

Declaring design tokens is not sufficient: complex-workspace CSS must consume at least five distinct tokens across the page, header, surfaces, controls, spacing, radius, or type. The body must establish a page background and text color, the product header must have intentional spacing plus a surface/border/elevation treatment, and the base button—not only its hover state—must define a background and radius. A canvas preview must use at least two drawing operations including content-bearing text, image, or image-data rendering; a single solid rectangle is pixel activity but not meaningful preview evidence.

For a complex workspace with five or more semantic regions, layout declarations on an unused class do not count: the accepted workspace owner itself must define a real multi-column grid or wrapping flex layout, and responsive rules must change that owner rather than an orphan selector. A declared canvas preview is a drawing interface, not an HTML container. JavaScript must obtain its 2D context and perform visible drawing calls, or HTML must use a non-canvas preview surface; assigning canvas `innerHTML`/`textContent` cannot satisfy preview behavior. The bounded semantic adapter may retarget such an invalid canvas HTML write to an already-accepted output in the same region, but the cross-owner gate will still reject an undrawn canvas that remains declared.

For explicit repeated grid columns, the cross-owner gate estimates desktop region width from the accepted workspace owner's own `max-width`, column count, and gap, normalizing px/rem values. An estimated column below the 320px browser usability floor is rejected before atomic commit with actionable alternatives: widen the viewport-bounded owner, reduce the desktop column count, or use `minmax(320px, 1fr)`. An unused wide container or a numeric declaration on another selector cannot satisfy this interface.

Browser design diagnostics also measure horizontal overflow, control hit-target geometry, oversized media, empty feature regions, region width, the maximum number of workspace regions sharing a desktop row, blank canvas pixels, and visible status content. A five-or-more-region desktop workspace that still places at most one region per row, a majority of materially narrow regions, or an alpha-empty preview canvas is a UI quality failure. Capability-driven graph workspaces must show actual tree/node examples and preview-capable workspaces must expose a dedicated, visibly rendered preview surface. CSS must bound the workspace and media, use valid `calc(...)` arithmetic when needed, and set an explicit control minimum height. These geometry and content checks prevent giant raw images, empty cards, or a styled but functionally blank canvas from satisfying visual density alone.

Computed-style and canvas-detail diagnostics also reject a product header with no spacing/surface/border/elevation treatment, a majority of buttons retaining zero-radius browser-default styling, and a preview canvas with at most three sampled opaque colors after its action runs. These are intentionally conservative anti-default/anti-solid-block checks; they do not prescribe a palette or visual theme, but they prevent raw browser chrome and a single color rectangle from being promoted as designed evidence.

Before capturing visual evidence, the browser runner exercises the first declared preview action when one exists and records `preview_action_exercised`; blank-canvas diagnostics are measured after that interaction. This keeps source assurance and customer workflow control aligned: drawing code that is never reachable still fails, while a valid click-driven preview is judged after the real action rather than only at initial page load. CSS feedforward also exposes a 320px desktop region-width floor and at least two regions per desktop row for complex workspaces; these are measurable usability bounds, not a fixed visual theme.

When screenshot capture fails, the UI evidence status may be `skipped` or blocked, but the discovery-derived domain vocabulary and capability groups remain attached to `ui_smoke`. ## ProviderJob issue-level partial improvement acceptance

Post-build Provider repair remains on the existing split-file ProviderJob execution path. Each returned owned leaf is evaluated against the issue facts bound into its repair bundle. A delta may advance the candidate lineage when at least one corresponding deterministic coherence failure disappears or measurably decreases, even if a different issue on the same path remains.
