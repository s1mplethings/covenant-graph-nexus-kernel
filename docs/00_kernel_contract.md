# CGKN Kernel Contract

This contract defines the stable kernel boundary for CovenantGraph Nexus Kernel. Future changes may add capabilities around the kernel, but they must not replace the generation mainline or bypass the safety and delivery boundaries described here.

## Kernel Responsibilities

CGKN Kernel is fixed responsible for:

1. Telegram entry for user project intake and generation confirmation.
2. `agent_session.jsonl` persistence for user messages, backend dialogue events, planner events, runner actions, and tool results.
3. `whiteboard` as the shared state surface for frontdesk, backend dialogue, planner agent, and generation agents.
4. `backend_dialogue_loop` as lightweight analysis and whiteboard update only; it is not a gate.
5. Running Telegram default project generation through API/provider project generation, provider output validation, post-build finalization, canonical evidence production, required user review, `local_packager`, public delivery gate, delivery receipt, active project binding, then canonical final verdict.
6. Keeping `pipeline_manifest`, `pipeline_planner_agent`, and `dynamic_pipeline_runner` as a support/experimental planning lane, not the Telegram default final project generator.
7. Using a CFO-controlled module plan inside `pipeline_manifest` when the support lane is explicitly used: the `cfo` role owns module planning, handoff order, acceptance interpretation, evidence review, and delivery readiness.
8. Allowing CFO support agents only inside the manifest as advisory context/risk maintainers, such as a context database and risk register. Support agents do not own Telegram default project generation, final route, implementation authority, or final delivery readiness.
9. Treating planning-only outputs such as `PRODUCT_PLAN.md`, `MODULE_PIPELINE.md`, `CFO_CONTEXT_DB.json`, `README.md`, or `TEST_REPORT.md` as planning/support artifacts unless provider project generation plus post-build finalization produces a runnable project surface and evidence.
10. Using `local_agent_actions` and `local_agent_skills` as the only tool execution boundary.
11. Using `local_packager.package_project` as the only formal delivery exit.
12. Treating the frozen, self-hashed canonical `delivery_manifest.json` as package evidence only after its inspector independently recomputes the current candidate/source hash, final ZIP hash, ZIP entry hash, evidence hashes, identity binding, and manifest/package delivery-directory binding. Canonical fields are reserved and cannot be replaced by extension metadata.
13. Allowing `dynamic_pipeline_runner` to recover complete actions from malformed or truncated agent JSON only inside the same manifest step, record the parse failure, and require a repair turn before that step can pass.
14. Allowing configured local models only as a model-source optimization. By default, local models may write public frontdesk/status replies only; generation-affecting local tasks such as customer classification, backend dialogue, planner, component generation/repair, CFO planning, context support, risk support, foundation, or QA must be explicitly enabled and must remain inside the same provider-output-validation/manifest/runner/evidence boundary. The Telegram service launcher may explicitly enable these reviewed tasks for a user-selected local-first deployment. Local component generation/repair must enter through the existing provider text call, produce parseable JSON, pass the same component ownership and output validation, and continue through post-build finalization, `local_packager`, and `public_delivery_gate`; it is not a second generation or delivery route. Invalid local output may fall through to the configured API provider but may never be promoted directly. When a local-model task is enabled, the router may auto-start the configured Ollama runtime (`CGNK_AUTO_START_OLLAMA`, enabled by default) before calling the model; this is runtime readiness only, not a generation route.
15. Recording critical setup questions for any explicitly required external, local, hosted, data, model, automation, security, storage, or runtime capability. These questions are shared context and acceptance constraints, not a new gate or generation route.
16. Recording a project-level capability strategy for core capabilities, advanced-method candidates, obvious route differences, and acceptance limits. This is universal planning context for the same manifest/runner flow, not a project-type-specific generator.
17. Wrapping Telegram user-facing narration in an action-based public expression layer. Public replies may describe what will be built, why input is needed, how testing works, what evidence will be shown, and how the user can continue or revise; this does not create a new formal generation path.
17. Requiring every formal `pipeline_manifest` to cover Product Studio evidence stages: `product_plan`, `technical_plan`, `build`, `test`, `review`, and `package`.
18. Auditing quality evidence before `package_project`, including `TEST_REPORT.md` and `DELIVERY_NOTES.md`, and recording missing evidence as warnings instead of hiding it.
19. Waiting for explicit user start confirmation when backend dialogue finds soft questions, critical questions, missing required inputs, or complex/high-uncertainty domains. These questions are not hard gates once the user explicitly starts; they become assumptions and delivery warnings.
20. Running public delivery gate before any final public delivery. The gate verifies canonical artifact schemas, hashes, run id, candidate hash, commit SHA, package integrity, and required attachment evidence. Missing required tests, runtime, previews, local models, datasets, or receipts produce canonical `NEEDS_REWORK` or a specific `BLOCKED_*` status.
21. Treating only `local_packager` final package output as the final delivery zip. `delivery_fact_check` records `any_zip_found` separately from `final_package_exists`; samples, fixtures, uploads, test data, and arbitrary `.zip` files must not satisfy final package delivery.
22. Sending only user-facing media/package artifacts by default in Telegram public delivery: `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`, `.mp4`, `.webm`, and `.zip`. Internal `.md`, `.json`, `.txt`, `.log`, manifest, report, and ledger artifacts stay inside the evidence bundle unless explicitly requested. Placeholder, mock, or fallback media cannot satisfy requested screenshots, backgrounds, sprites, generated images, or demo evidence.
22. Auditing build completion before a build step can pass. A worker build step must not report `pipeline_step_result.status=ok` unless it produced a real runnable project surface, including `app.py` or `main.py`, dependency metadata such as `requirements.txt` or `pyproject.toml`, source files, tests, and required visual evidence.
23. Auditing QA completion before a QA/test step can pass. If `TEST_REPORT.md` contains `NO TEST EXECUTED` or does not list real test commands, the step must be `rework_blocked`, not `ok`.
24. Treating Telegram `generation-mode=simulator` as preflight-only. It must record a recoverable blocked result and must never produce a public PASS, package, or delivery manifest.
25. Rejecting provider output locally when it is empty, unsafe, generic/template metadata, placeholder implementation, or missing `README.md`, `TEST_PLAN.md`, and a runnable entrypoint.
26. Preserving validated provider component PASS checkpoints across retryable transport failures. Failed attempts use separate diagnostics, while semantic repair invalidates stale component checkpoints once before regeneration.
26. Recording a deterministic delivery inclusion manifest in `delivery_manifest.json`, including POSIX relative paths, byte sizes, content hashes, and the final zip path. Formal `visual_required`, `media_required`, and `user_review_required` values come from workflow requirements rather than artifact presence. Local split-manifest normalization and formal manifest validation share the same component-id extraction and accept the bounded equivalent `component: {id, files}` wrapper while still enforcing the expected component id, required paths, and ownership. Source validation rejects explicit placeholder-implementation and TODO-comment claims but does not confuse functional placeholder attributes or the task status label `Todo` with unfinished work. Ollama code generation uses an explicit bounded prediction length and context window so a valid file request cannot run indefinitely; both remain environment-configurable within guarded limits. Component repair prompts preserve the selected requirement's persistence and integration contract and must not impose a fixed backend API or prohibit browser-local persistence. A native split frontend must contain a meaningful visible body, index generation must immediately enforce the exact split-manifest script/stylesheet paths, the merged frontend must resolve every local asset reference, task-board JavaScript must cover its explicitly requested behaviors, and generation must reject literal DOM references that are neither present in the HTML nor explicitly created by JavaScript. Browser module validation parses only actual static or dynamic `import` syntax; identifiers such as `importVideo` cannot be interpreted as package imports. Generated tests must inspect behavior in the file that owns it and cannot treat the Python `__main__` module guard as a function. An empty shell or structurally broken page must be repaired before browser screenshot or video evidence is accepted. Visual smoke uses actual non-empty DOM text, domain markers, browser errors, and decoded image evidence rather than an arbitrary long-text threshold, so concise valid interfaces are not classified as blank. `CGKNUserReviewRequest` binds `visual_required` explicitly in its self-hash; the request producer and inspector never infer it from screenshots, visual evidence files, presentation results, review files, or adaptive judgment. When true, the frozen request binds canonical test/runtime/visual evidence and a successfully sent, decoder-validated screenshot with the canonical screenshot hash; when false, visual evidence and screenshot roles cannot silently expand the review scope. Candidate-bound user review then requires Telegram update/message/date/from-user identity bound to the expected reviewer. The formal rule is that session booleans and text substrings are not review truth; neither are session request dictionaries or file presence. The review inspector independently checks request/ref hashes, visual scope, reviewer identity, timestamp order, evidence identity, presentation artifacts, and the durable replay ledger. Public-gate and send runtime state stays in session/truth-ledger records and must not mutate the frozen canonical manifest; the package path, ZIP hash, entries hash, and manifest artifact hash are rechecked immediately before the package document send.
   The formal Telegram evidence checkpoint sender re-inspects the frozen request and canonical visual evidence immediately before sending, permits only the canonical screenshot path/hash, treats only normalized successful Telegram returns as sent, and freezes optional Telegram message/chat metadata into the presented artifact. Exceptions, invalid returns, partial presentation, or pre-send changes produce `presentation_failed` before approval or packaging.
27. Never duplicating one sample image into screenshot, background, and sprite evidence, and never generating fallback media merely to satisfy a requested image capability.
28. Allowing only factual failures to force `BLOCKED`: missing project output, unsafe paths, missing claimed Telegram attachments, placeholder-only generation, or explicit provider failure. A final delivery without a packager zip cannot be `PASS`, but may remain available for user review. Telegram must not mark final delivery as delivered until the allowed public artifact set has actually been sent; final verdicts require the final package zip send to succeed.

`public_delivery_gate` remains a compatibility name for the wrapper that verifies canonical evidence, package integrity, and delivery receipts; it is not a second delivery route.

## Pipeline Module Mutation Contract

Replaceable support-lane modules may be changed only through reviewed repository changes that preserve their declared `contract()` boundary. This includes directly modifying, generating, or deleting bounded modules. truth modules—canonical evidence producers, inspectors, package and delivery gates—are not replaceable support modules and cannot be bypassed by a candidate bundle or module stub. A candidate bundle remains non-final until the canonical mainline independently validates and promotes it.

When the public delivery gate returns `rework_blocked`, Telegram session state must clear `generation.package_path`. A rejected or superseded package may remain on disk for diagnostics, but its path cannot remain advertised as a deliverable session artifact.

## Kernel Prohibitions

CGKN Kernel must not:

1. Reconnect the Telegram formal generation mainline to `generate_project.py`.
2. Reconnect the Telegram formal generation mainline to the raw `run_local_pipeline.py` CLI or any route that bypasses provider output validation, post-build finalization, `local_packager`, `delivery_fact_check`, or `agent_delivery_judgment`.
3. Restore `simulator` as the formal generation mainline.
4. Turn `backend_controls` back into an execution queue.
5. Treat `blocking_questions` or `soft_questions` as a hard gate for generation.
6. Allow `pipeline_manifest` to execute arbitrary Python.
7. Allow generation agents to modify CGKN kernel files.
8. Bypass `local_packager` or forge delivery completion.
9. Treat `agent_generated_pipeline` or CFO document outputs as Telegram default final project generation.
10. Count any fallback preview, placeholder, stub, procedural substitute, simulated result, or basic implementation as satisfying an explicitly requested core capability that requires a mature method, configured model, external API, local service, data source, automation engine, or runtime evidence.
11. Encode a project type, industry, object, or domain label as a special formal generation path. Domain labels may only help infer underlying capabilities; provider project generation remains universal.
12. Automatically start complex or under-specified project generation merely because soft questions are non-blocking. Non-blocking means the user may explicitly start with assumptions, not that the system starts by itself.
13. Treat internal reports, manifests, ledgers, or README-only folders as user-facing delivery results.

## Stable Flow

```text
Telegram
-> customer request
-> agent_session.jsonl
-> whiteboard / backend_dialogue_loop
-> API/provider project generation
-> provider response staging
-> canonical response -> decision -> patch -> production-candidate application
-> provider output validation
-> post_build_finalize
-> production-candidate provenance + provider causal trace
-> canonical test/runtime/visual evidence
-> user review when required
-> local_packager
-> public_delivery_gate
-> delivery_receipt
-> bind active project
-> final_verdict.json
```

The kernel is stable. The pipeline is agent-generated per project. The project itself is fully generated inside the bounded project directory. Skills are controlled capability modules. The whiteboard is the shared communication surface between intake, planning, generation, and delivery.

For generated projects with a visual surface, the same reviewed Provider route runs design discovery before component generation. `scripts/design_research_agent.py` searches multiple bounded reference classes, records source URLs and reuse boundaries, compares three visual directions, and selects one project-specific design contract. The generation-context librarian exposes only the bounded selected direction, design tokens, relevant references, and interaction/accessibility constraints to frontend, media, and design-document leaves. Provider output must include `docs/design_research.md` and `docs/design_system.md`, and component plus assembled-project validation rejects missing token reuse, responsive layout, keyboard focus, interaction feedback, reduced-motion behavior, source traceability, or selected-direction implementation. These are support planning and source-quality receipts only: they cannot replace canonical browser visual evidence, user review, packaging, or public delivery PASS, and they do not create another generation or delivery route.

## Consolidated Kernel Rule

CGKN Telegram default generation uses API/provider project generation as the formal project-file generator. The provider route must write real project files, validate provider output, run post-build finalization, produce canonical test/runtime/visual evidence, record required user review, package through `local_packager`, pass public delivery gate, record delivery receipts, and write the canonical final verdict before claiming completion.

Before canonical test/runtime/visual evidence, the formal provider route must freeze one `CGKNProductionCandidateProvenance` from `scripts.telegram_live_bridge.start_generation_from_income -> run_provider_generation_job -> provider validation -> source-changing post-build`. It binds a unique run and candidate, the repository commit, the real customer candidate path, ordered self-hashed stage receipts, provider artifacts, and the independently reproducible candidate source manifest/hash. `scripts.production_candidate_provenance.inspect` must reread disk and recompute the manifest and candidate hash. Session/context booleans, `source_inspection="PASS"`, adaptive judgment, fixture output, acceptance output, and repository commit hashes cannot authorize this provenance. A provenance failure short-circuits canonical evidence inspection and adaptive delivery judgment.

Canonical source enumeration prunes the same root tool environments, caches, symlinks, and junctions that are excluded from the candidate hash before descending into them. Excluded dependency environments such as `.cgkn_test_env` cannot affect the hash and must not be recursively scanned during provenance or causal-trace inspection.

Canonical customer-runtime evidence stores at most the bounded observation body and hashes those exact stored bytes. It must not hash an unbounded pre-truncation response while recording only a truncated response, because the inspector must be able to reproduce every evidence hash from the persisted artifact.

The provider interface writes only to a run-unique response staging directory. `scripts.telegram_live_bridge.py` is the sole formal `CGKNProviderCausalTrace` producer: before invoking the provider it freezes the request plus the production candidate's pre-provider manifest/hash; after return it refuses any out-of-band candidate mutation, freezes canonical response content, deterministically extracts implementation decisions, builds per-file hunks with byte-exact before/after content and hashes, applies those hunks to the production candidate, records the application receipt, binds any subsequent post-build source delta, and finally binds the same production provenance identity. `scripts.provider_causal_trace.inspect` rereads every artifact and the candidate from disk, reconstructs response, decisions, hunks, patch application, post-build delta, source manifests and candidate hashes, and checks the ordered provider-generation, provider-validation and post-build receipts. Provider IDs, caller booleans, session state, adaptive judgment, acceptance output, and direct provider writes to the final candidate cannot substitute for this chain.

API/provider detection remains required operational support. The canonical persistent credential is the Windows User-level `CGKN_OPENAI_API_KEY`; it takes precedence over stale inherited process values, while the explicit one-run `CGKN_OPENAI_API_KEY_OVERRIDE` remains the only higher-priority override. Provider credentials must never be recovered from `.agent_private/NOTES.md`. Credential replacement must atomically set the canonical User value, clear User-level `CGNK_OPENAI_API_KEY` and `OPENAI_API_KEY` compatibility copies, scrub legacy note secrets, and report unresolved process or machine conflicts without logging their values. `gpt-4.1-mini` smoke tests may call `https://api.gptsapi.net/v1/chat/completions`, and retryable provider transport errors such as `SSLError`, `SSLV3_ALERT_BAD_RECORD_MAC`, timeouts, connection resets, 502, 503, 504, or empty responses must be retried before declaring NEEDS_REWORK. Provider support must not write API keys to logs or project files, and must not create fake delivery assets after retry exhaustion.

The `pipeline_manifest` is retained as an agent-generated support/experimental lane from `whiteboard` and `agent_session`. `dynamic_pipeline_runner` may interpret that manifest through `local_agent_actions` and `local_agent_skills`, but Telegram default generation must not treat CFO documents alone as final project generation.

Post-build finalization is part of the provider route. Formal Python test execution must honor a valid, project-local `[tool.pytest.ini_options].testpaths` declaration before falling back to `python -m pytest tests`; declared paths must be relative, traversal-free, and present. This lets a docs-first project distinguish its reviewed acceptance suite from archived or exploratory generated tests without silently skipping the declared suite. It must write `TEST_REPORT.md` with `commands_run`, `exit_code`, stdout summary, and stderr summary. If requested screenshots or generated images are missing, it may attempt to collect real evidence, but must not synthesize fallback media merely to satisfy delivery. Placeholder, blank, or pure-color images must not satisfy requested background or sprite evidence. Packaging normally creates `final_project_bundle.zip`, then runs factual checking and adaptive judgment.

The complexity contract is phase-aware: candidate post-build validation checks discovery, project structure, executable evidence, screenshots, and quality gates without requiring the future `final_project_bundle.zip`. The delivery-phase checker retains that bundle requirement. This prevents packaging output from becoming a circular prerequisite for candidate approval while preserving `local_packager` as the only delivery exit.

A lower-case provider-generation `status=pass` means only that reviewed provider files were materialized and the semantic generation review passed. The result must also record `workflow_state=generation_completed`, `evidence_status=NOT_EVALUATED`, `post_build_required=true`, `packaging_required=true`, `final_delivery_allowed=false`, and `not_final_delivery=true`. Telegram then continues through production provenance, post-build canonical test/runtime/visual evidence, `local_packager`, and the public delivery gate. Direct generation output must never be interpreted as formal delivery `PASS`.

Collected media must retain its actual evidence type. A screenshot or generic example image cannot be copied and relabeled as both a generated background and a generated sprite. If a requested local image model is unavailable, finalization records `missing_config`; canonical evidence decides whether the honest result needs `NEEDS_REWORK`, `NOT_EVALUATED`, `PASS_WITH_LIMITS`, or a specific `BLOCKED_*` status.

The modular post-build wrapper owns the `video_requested` option. It must consume that option before calling the legacy candidate-finalization implementation, then pass the explicit value only to video evidence collection; optional evidence policy must not leak as an unsupported legacy keyword.

The default manifest shape is CFO-controlled and Product Studio disciplined: `product_plan -> technical_plan -> build -> test -> review -> package_project`. A step may merge stages when appropriate, but the manifest must still cover `product_plan`, `technical_plan`, `build`, `test`, `review`, and `package`. The planning stages must produce `PRODUCT_PLAN.md`, `OUTPUT_CONTRACT.md`, `TECHNICAL_PLAN.md`, and `BUILD_PLAN.md`; QA must produce `TEST_REPORT.md`; review must produce `DELIVERY_NOTES.md`; and `package_project` remains the only delivery exit. Specialist agents may build modules, and support agents may maintain `CFO_CONTEXT_DB.json` or `CFO_RISK_REGISTER.md`, but they do not own the formal route or final delivery readiness.

Build and QA steps are hard evidence boundaries inside `dynamic_pipeline_runner`. README-only/docs-only output cannot pass a worker build step. `TEST_REPORT.md` with `NO TEST EXECUTED`, `commands_run: none`, or missing real commands cannot pass a QA/test step. These failures must be recorded as `pipeline_step_result.status=rework_blocked`, not hidden as successful steps.

Before packaging, `dynamic_pipeline_runner` must audit quality evidence. Missing `TEST_REPORT.md` or `DELIVERY_NOTES.md` may be repaired once with an honest warning artifact, but packaging cannot hide the gap. `local_packager` records `quality_evidence` in `delivery_manifest.json`, and Telegram delivery replies must summarize whether test report, review notes, and preview evidence exist.

Telegram delivery uses public delivery gate followed by `CGKNDeliveryReceipt`. The gate outputs canonical status, missing evidence, verified hashes, and retryable failure details without making a separate final PASS decision. `PASS_WITH_LIMITS` must disclose its limitations and cannot satisfy public final delivery. `NOT_EVALUATED` is non-final. `BLOCKED` and the specific `BLOCKED_*` statuses cannot be overridden by the agent. Public attachments remain restricted to safe, existing media/package files listed by `can_send_artifacts`. Safe delivery roots include the project directory plus explicit packager/run delivery roots recorded in the manifest; absolute paths are resolved before boundary checks.

`scripts/canonical_delivery_receipt.py` is the sole producer and inspector for the authoritative project-root `delivery_receipt.json`. Telegram final delivery may enter `delivered` only after structured API receipts bind every formally required attachment to the expected chat and the on-disk receipt inspector returns `PASS`; sent lists, truth ledgers, booleans, and session flags are not substitutes.

`scripts/final_internal_acceptance.py` is a diagnostic fixture exerciser for its fixed Task Studio project, fixed Workers, replan, recovery, startup, runtime, and browser scenarios. It is not a production entry or a formal evidence producer, and its self-hashed outputs cannot authorize a formal Gate `PASS`. `scripts/formal_mainline_acceptance.py` is the read-only total-acceptance entry: it consumes existing production artifacts, binds the repository and customer candidate identities separately, invokes the registered inspector on disk, and emits `CGKNFormalGateStatus` without copying or relabeling source evidence. A missing production artifact or inspector remains `NOT_EVALUATED` or `NEEDS_REWORK`. `scripts/final_contract_unification_acceptance.py` is only a deprecated compatibility facade for this reader.

When an agent reply is malformed or truncated, the runner may salvage fully closed actions and execute them, but it must keep the step in repair until strict JSON succeeds. This is parser resilience inside the current manifest step, not a separate generation path.

Local-model routing may reduce provider cost for low-risk tasks. Public reply tasks must not alter `whiteboard`, `pipeline_manifest`, generation actions, or delivery readiness. Generation-affecting local tasks must be opt-in and must stay inside the same `pipeline_manifest` and `dynamic_pipeline_runner` boundary. They must not bypass manifest validation, `local_agent_actions`, `local_packager`, or final delivery evidence.

If an enabled local-model task uses Ollama, the router may find `ollama.exe`, run `ollama serve`, and wait for `OLLAMA_HOST` to respond before sending the request. `CGNK_OLLAMA_EXE` or `OLLAMA_EXE` may override the executable path, and `CGNK_AUTO_START_OLLAMA=0` disables this readiness helper. Auto-starting Ollama does not enable additional tasks by itself and does not change the Telegram default provider generation route.

Configured local models do not create a new formal generation path.

The default Telegram model-routing profile is `hybrid_safe`. In that profile, local models own bounded public replies, status, classification, backend dialogue, pipeline planning, CFO/context support, and risk support as advisory context. Formal component generation, repair, and semantic QA go directly to the API provider; local runtime tools still own deterministic syntax checks, tests, browser evidence, media validation, packaging, and delivery gates. `local_first` remains an explicit experimental opt-in and is never added by the service launcher implicitly. `api_only` disables all local tasks. `custom` preserves a caller-supplied task list. Every provider-stage call records `provider_responsibility_route` with the selected profile, task, owner, and direct/fallback route.

Local task model selection may use `CGNK_OLLAMA_REASONING_MODEL` for classification/planning/review and `CGNK_OLLAMA_CODE_MODEL` for bounded component generation/repair, with `CGNK_OLLAMA_MODEL` retained as the common fallback. Local provider output must satisfy the stage-specific component id, file manifest, target path, and non-empty content contract before it can enter the formal chain; a split manifest may omit its redundant component field because the caller binds the component and independently checks every path against canonical ownership, but a present mismatched component is rejected. An exact single-key wrapper whose key equals the already-bound canonical component id may be normalized before validation; arbitrary or mismatched wrappers remain invalid. Split component manifests must include the canonical component's minimum runnable paths; missing paths and ownership violations are repairable component failures. Explicit data storage uses the dedicated `data` owner and does not share `data/**` with `backend`. Contract-invalid local output receives up to three bounded correction attempts (four total local attempts), with all earlier source-validation failures retained in each later correction, and then falls through to the existing API provider route. Large repair prompts remain eligible for manifest/per-file splitting; the presence of repair actions must not force an oversized monolithic provider request, and enabled local code tasks use `CGNK_LOCAL_COMPONENT_MAX_PROMPT_CHARS` as an earlier split threshold. A terminal component exception must retain the failing component id so semantic retry invalidates and regenerates the failed checkpoint instead of an unrelated component.

For complex projects, the selected requirement domain and discovery direction must agree before provider generation starts. The accepted discovery complexity contract enriches the reviewed canonical components with concrete required paths, stage names, shared-core boundaries, artifact schemas, planning documents, and explicit test-count floors, and that contract slice must survive manifest/per-file prompt splitting. Deterministic source checks override an unstructured model-QA pass: a domain mismatch, missing contract file, absent required stage, missing shared runner/job manager, insufficient collected tests, or failed post-build complexity inspection produces `NEEDS_REWORK` or a specific blocked status. These checks strengthen the existing provider validation and post-build finalization route; they do not create another generation or delivery route.

When a complex goal names a specialized evidence-analysis domain that is not one of the fixed generic product shapes, requirement decision and discovery must both preserve it as the same goal-derived specialized-analysis domain. The selected direction must carry an official-source research stage, reviewed and authorized acquisition, provenance validation, normalized evidence, explainable analysis, and human-review reporting. It must not silently substitute an unrelated media or data-quality product merely because that generic candidate has a high static score.

Leaf implementation-depth validation distinguishes executable behavior from interface declarations. Ellipsis-only or pass-only behavior in ordinary owned classes and functions remains a blocker, while methods declared directly by a Python `typing.Protocol` are accepted as typed interface contracts. This exception is limited to protocol methods and cannot turn an empty concrete implementation into accepted evidence.

Implementation-depth metrics are source-type aware. CSS and SCSS leaves measure concrete selector blocks, property declarations, and conditional at-rules rather than JavaScript function/class patterns. A substantive stylesheet can therefore satisfy its owned presentation contract, while an empty or comment-only stylesheet still fails the configured line, statement, and behavior thresholds.

Leaf feedforward carries a bounded interface projection rather than repeating the complete local registry. The authoritative catalog preserves project path, content identity, Python class names, callable signatures, constructors, imports, and applicable web/schema interfaces, while omitting duplicated per-parameter contract dictionaries. It defaults to eight entries and 8000 serialized characters, with bounded per-run overrides through `CGKN_PROVIDER_INTERFACE_CATALOG_MAX_ITEMS` and `CGKN_PROVIDER_INTERFACE_CATALOG_MAX_CHARS`; the complete registry remains local and the librarian selects additional relevant evidence within its own independent budget.

Once split generation has accepted a component file manifest, a failed leaf writes that manifest and its completed-file list into the pending repair plan. In-process component retry must promote that pending plan and reuse the same manifest instead of asking the provider to redesign the component. This keeps leaf checkpoint hashes stable, retries the failed leaf and its dependency-scoped consumers, and prevents already verified siblings from being discarded by manifest drift.

Every newly assembled or checkpoint-reused provider component must pass an independent deterministic component quality validation before its files can feed downstream generation. The validation rechecks Python syntax and implemented import interfaces, JSON syntax, and exact local JavaScript/TypeScript module paths and symbols, including local re-export bindings and unimported sibling helpers. Python validation also follows constructor-annotated dependencies stored on `self`, rejects calls to missing methods on those known generated classes, rejects unsafe direct `eval`/`exec`, and rejects explicit executable-placeholder comments. A cached component whose current validation fails is invalidated and regenerated rather than trusted from its historical PASS. After component merge, the same language-aware checks plus cross-component path ownership run again for the complete file set. These receipts are support evidence only, but a failed receipt blocks provider-generation quality success and cannot be overridden by provider self-test or semantic-review prose.

A pending file manifest is component-owned repair state. Split generation may reuse it only when both the pending stage is `component_file_generation` and the pending `component` equals the component currently being generated. A backend pending manifest must never become a frontend, tests, or docs leaf graph; cross-component pending-state reuse is an ownership violation and must fall back to planning that component's own manifest.

For every non-static project whose accepted complexity contract declares `required_pipeline_stages`, the backend manifest must contain both `backend/stages.py` and `backend/orchestrator.py`; those paths are required before file generation rather than discovered only by final semantic review. The frozen stage names become deterministic public symbols in `stages.py` even when a provider manifest compresses them behind one generic dispatcher. Manifest normalization promotes that file to high complexity before bounded-submodule expansion, groups stage symbols into small stage leaves, and keeps `stages.py` as the compatibility facade. For the canonical backend paths it replaces provider-invented cyclic dependency edges with one deterministic DAG: domain and artifact primitives first, persistence/preview and stage implementations next, the stage facade then orchestrator, and `main.py` last. An unresolved provider cycle therefore cannot generate the application entry before the APIs it must assemble. `orchestrator.py` is a bounded medium-complexity coordination leaf because stage behavior lives in the split stage modules; it must still publish the single canonical `ProjectOrchestrator` contract, validate and pass state through the ordered stage graph, and return inspectable outcomes. Provider-invented synonymous orchestrator class names are discarded rather than preserved as pass-only compatibility shells. This preserves the reviewed stage contract and prevents a multi-stage project from collapsing into a few shallow domain files or one oversized leaf while avoiding duplicated stage logic in the coordinator.

They do not block the manifest/runner flow, but they must be reflected in acceptance criteria so fallback output is not misreported as satisfying the requested capability.

Telegram intake uses `should_auto_start_generation` before starting formal generation from a new project request, project update, or attachment. If `needs_direction_confirmation`, `soft_questions`, `critical_questions`, `missing_required_inputs`, a complex/high-uncertainty domain, or low confidence is present, intake records `generation_start_waiting` and waits. If the user explicitly says to start, unanswered questions and missing inputs are written into `generation_context_snapshot` as assumptions and warnings; outputs with missing real inputs must be partial/scaffold evidence, not full validation.

Capability strategy fields such as `capability_strategy` and `capability_research_targets` guide CFO planning and support agents for every project. They must describe underlying capabilities and advanced-method candidates, not project-type-specific branches. They do not authorize legacy pipelines, arbitrary execution, or bypassing manifest validation.

Public narration is allowed only at Telegram reply boundaries. It may redact internal terms and present progress through concrete actions and evidence, but the underlying Telegram default execution remains `api/provider project generation -> provider validation -> post_build_finalize -> canonical evidence -> required user review -> local_packager -> public_delivery_gate -> delivery_receipt -> bind active project -> final_verdict.json`.

Fallback to a single agent loop is allowed only when pipeline planning or runner execution fails, and it must record `pipeline_fallback`.

Cross-file Python callable mismatch feedback includes the authoritative expected signature so repair does not have to infer positional, keyword-only, variadic, or required parameters. Uniform stage-leaf prompts also require every return branch to directly yield a literal result mapping with a literal `success` or `error` status and a mapping output. Orchestrator repair publishes the exact statically inspectable `result = stage(state)` loop shape and result-field reads. Application-entry repair feedback publishes the exact required stage-list expression and requires a literal list or tuple so the executable graph remains statically inspectable. HTML expected symbols are translated into exact visible literal `id` contracts, while CSS `--*` expected symbols become exact `:root` custom-property contracts; language-specific publication meaning is never left for a Provider to guess. HTML ids, CSS tokens, JavaScript exports, local module imports, and unimported sibling calls are checked at each leaf boundary rather than deferred to whole-component review. Frontend CSS generation receives the same measurable design-system signals used by the final quality gate: eight or more tokens, a responsive focal composition, visible focus treatment, and reduced-motion handling. A high-complexity JavaScript product leaf with at least three published symbols is deterministically split into bounded symbol-owner modules plus its compatibility facade even when it falls below the general six-symbol expansion threshold. Bounded JavaScript symbol owners receive both nonblank-line and source-character ceilings in their initial prompts and validation receipts; any remaining unsplit high-complexity JavaScript leaf is bounded the same way so it cannot consume the entire Provider token allowance before validation. On an outer component retry, the formal route reloads the latest pending leaf target before computing the repair closure, preserving newly completed prefix checkpoints instead of replaying a stale earlier leaf. Larger responsibility sets must therefore become manifest submodules rather than a larger context window. These are generic leaf-repair rules and cannot become project-specific compatibility patches.

## Legacy Code Policy

Legacy provider pipeline code must not bypass post-build finalization, `local_packager`, or public delivery gate.

Legacy CLI may exist only under `legacy/` or as a thin wrapper.

Telegram formal generation may call the reviewed API/provider project generation implementation restored from the old provider chain, but it must not bypass post-build finalization, `local_packager`, or public delivery gate. `generate_project.py` and `simulator` remain disallowed as Telegram mainline.

### Pending leaf completion

When the exact leaf named by a pending component-file repair passes its boundary and publishes its interface, CGKN immediately archives that pending target as completed. A later interruption therefore cannot keep invalidating an already repaired leaf while another downstream leaf is being generated; any later exhausted failure writes its own new exact pending target. Python component-level publication checks follow Python module binding semantics: top-level `import` and `from ... import ...` names count as published interfaces, so a validated compatibility facade is not falsely rejected after its leaf boundary accepts the same exact re-exports. Within `tests/test_*.py` only, `test_*` methods directly owned by a top-level test class also satisfy test-manifest symbols because unittest and pytest collect them; product modules retain module-level publication rules. Required Python test manifests are normalized to explicit existing upstream providers before leaf graph construction: pipeline/integration tests bind stages and orchestrator, artifact tests bind the artifact store, cancel/resume tests bind the orchestrator, degraded-mode tests bind adapters, and application tests bind the real entrypoint. Only paths already present in the prior manifest may be selected; this feeds exact APIs through the librarian instead of letting tests invent undeclared modules. Python leaves with no declared local dependencies receive an explicit empty local-import contract: librarian excerpts remain contextual evidence and cannot authorize imports. Design-document traceability blockers always publish the exact required design-document paths as affected files, so missing source URLs, selected-direction naming, or anti-copying boundaries regenerate those documentation leaves instead of causing a cache-only component retry loop. Each regenerated design-document leaf receives a highest-precedence documentation contract from the bounded design-research context: it must reproduce the exact selected-direction name, cite at least three supplied source URLs, and include the canonical anti-copying boundary without paraphrase. This keeps source discovery in the librarian while making the leaf's quality obligations deterministic. The semantic repair compiler deduplicates identical blockers before planning. Any structured blocker carrying file evidence keeps those paths through the generic route, maps each path to its canonical component owner, and generates file-level actions; it may widen to a component only when no usable file evidence exists. Pending semantic repairs retain their parsed structured blockers on resume, including file hints and ownership evidence, instead of recompiling from lossy message strings. Artifact-store and artifact-contract leaves receive the exact required record fields and stage-artifact names from the frozen complexity contract as a highest-precedence schema contract. Their leaf boundary rejects omitted field/artifact names, opaque-byte stores, dummy or placeholder behavior, and pass-only documentation examples before those files can enter a component checkpoint. Code must validate structured records, and documentation must describe concrete producers, consumers, validation, and failure semantics.

When the frozen complexity contract requires both background and sprite generation, manifest normalization enriches the existing Provider component route rather than creating another path. `backend/image_adapters.py` must expose an executable deterministic offline PNG generator plus an adapter boundary and owns the concrete PNG write; `scripts/capture_workflow.py` must expose separate background and sprite workflows with prompt/seed/hash/type/path metadata, invoke those exact generator methods, then verify the returned path exists, read its bytes, validate the PNG signature, and compute the recorded hash before returning success; `demo/run_fixture.py` must generate at least two of each and verify PNG validity, hash diversity, and sprite alpha. The fixture receives the exact required stage-artifact names as a literal `REQUIRED_STAGE_ARTIFACTS` contract, executes the published application graph once through `main.initialize_app`, and must iterate, load, and validate every named JSON artifact without directly reconstructing `ProjectOrchestrator` or inventing private dependency helpers. This keeps orchestration in the application entry while the fixture owns runtime evidence materialization. This writer/verification ownership split prevents duplicate rendering in wrappers while keeping path-only success impossible. Capture validation is based on written-byte evidence rather than requiring the wrapper to rewrite a caller-selected filename or merely contain a `.png` token. Their leaf boundaries reject simulated-text success, fake bytes, missing adapter PNG writes, missing capture read-back checks, missing paths, and missing fixture evidence. The assembled-project deterministic complexity gate independently checks all three exact paths and routes any missing capability back to its owning leaf, including an inadequate upstream image adapter even when a semantic reviewer reports only a media symptom. If generated code imports `PIL`, the foundation dependency leaf and assembled-project gate require the `Pillow` distribution in `requirements.txt`; imports and install metadata cannot diverge. Optional external image providers may be unavailable only through honest degraded/error state; the offline default remains executable.

Both the leaf boundary and the assembled-project complexity gate enforce that ownership split consistently: the adapter must contain the concrete PNG write, while the capture wrapper must prove file existence, read the returned bytes, validate the PNG signature, and hash those exact bytes. The wrapper is never required to contain its own save/write call or a filename literal, and byte read-back without signature validation is still rejected.

The bounded capture-wrapper contract publishes the exact eight-byte PNG signature and the required `bytes.startswith(PNG_SIGNATURE)` rejection shape. This is a language-level interface invariant, not generated project content: it gives small models an unambiguous verification protocol while their returned wrapper source still comes from the reviewed Provider call and must pass the same leaf boundary.

The generated fixture contract likewise publishes a syntactically exact public import block (`hashlib`, `json`, `Path`, `initialize_app`, and both capture functions), requires every called helper to be defined before use, and recommends direct `Path.write_text(json.dumps(...))` artifact writing without f-string construction. These are bounded interface and syntax constraints; the Provider still owns the complete fixture implementation and its returned file must pass undefined-name, syntax, artifact, media, and runtime checks.

Generated pytest leaves treat fixture functions as dependency-injected values, never as the second `pytest.mark.parametrize` argument. The leaf AST boundary rejects a declared fixture referenced directly as `argvalues` and directs the same Provider leaf to request the fixture as a test parameter or supply a real iterable of cases. Generated media fixtures must decode PNG files before reasoning about pixels: transparency checks use Pillow RGBA alpha-channel extrema or pixels, and the leaf boundary rejects integer subscripting of variables populated by `Path.read_bytes()`. Compressed PNG offsets are container bytes, not decoded pixel evidence.

The media-fixture source boundary also requires decoded alpha-channel extrema with evidence that the minimum alpha is below 255; asserting equality to 255 proves opacity, not transparency. The fixture must contain a concrete structured-JSON write operation for required stage artifacts before it reads them back. These checks run during initial leaf generation and post-build repair, ahead of runtime evidence collection.

The bounded post-build fixture prompt publishes the exact evidence-write shape for small models: create parent directories, build a receipt derived from the application startup result with all frozen artifact fields, then call `artifact_path.write_text(json.dumps(receipt), encoding='utf-8')` before read-back. This specifies the interface protocol without supplying project-specific fixture content.

The fixture source boundary verifies that ordering as well as token presence: an artifact read-back or missing-file precondition placed before the structured receipt write is rejected. This prevents a superficially compliant but unreachable write from passing static validation and failing immediately at runtime.

For post-build repair, the same protocol is supplied as a named `required_stage_artifact_write_shape` that replaces the entire existing artifact loop. It explicitly forbids preserving a pre-write existence check, `FileNotFoundError`, or JSON read. Publishing a bounded generic control-flow scaffold is an interface constraint for small code models, not a project-specific generated-file patch.

The same two boundaries are reapplied to post-build file repair responses before any replacement is written. The repair prompt carries the pytest injection rule and decoded-image alpha rule whenever their target types are present, so runtime repair cannot bypass a constraint enforced during initial leaf generation.

Post-build Provider replacements use a bounded per-leaf output-validation retry loop. Every failed target file is requested, regenerated, and validated independently with its own accumulated boundary errors; this preserves the small-module generation contract even when one post-build run exposes several roots. No replacement is written until every requested leaf has passed, so the repair set remains atomic. A response omitting its one requested target or returning any additional file is rejected. Only a complete repair set that passes path ownership, syntax, pytest-fixture, media-decoding, and delivery-claim boundaries is written to the candidate.

Every Python post-build replacement also passes the same undefined-name analysis used by initial leaf generation. A replacement that calls an unimported library symbol, drops a dependency import, or otherwise leaves an unresolved name is rejected before it can overwrite the candidate and receives that exact name in its leaf-level retry feedback.

Post-build command diagnostics retain a bounded 12,000-character tail by default (configurable with `CGNK_POST_BUILD_COMMAND_OUTPUT_CHARS`, hard-capped at 20,000). This is large enough to preserve pytest traceback causes and the final failure summary together; a short summary-only tail cannot drive model-owned test repair. Diagnostic expansion does not change test status or substitute for the full on-disk stdout/stderr evidence.

The repair compiler then derives a bounded target-specific diagnostic excerpt for every requested leaf. A fixture leaf receives the structured fixture receipt and command traceback; a test leaf receives the pytest output window around its exact path; other leaves receive the global post-build window around their path. Per-leaf Provider requests carry that focused excerpt separately from the short global summary, so one verbose failure class cannot evict another target's root cause.

Provider test manifests cannot transfer production-interface names into test-leaf ownership. For Python files under `tests/`, normalization retains only exact `test_*` identifiers in `expected_symbols`; names such as a production `Stage`, parser, adapter, or orchestrator must be imported through the declared upstream dependency interface and exercised, never redefined inside the test merely to satisfy a symbol counter. Test responsibilities and acceptance checks remain intact, so removing false ownership does not weaken behavior or depth validation.

When a completed component-file repair is stored inside a semantic-repair wrapper, pending-leaf archival must unwrap the nested `repair_plan`, match the exact component and target, mark both records completed, and remove the active pending file before downstream work. A restart cannot force-regenerate an already validated leaf merely because the pending record was wrapped.

Leaf generation concurrency follows the active provider owner. When `component_generation` is assigned to the local model, the default is one leaf worker (optionally bounded to two with `CGNK_LOCAL_PROVIDER_LEAF_MAX_WORKERS`) so a single Ollama runtime is not flooded by external-provider concurrency assumptions. API-owned generation keeps the existing `CGKN_PROVIDER_LEAF_MAX_WORKERS` default of three. Validation, checkpoints, and repair semantics are identical under either scheduler.

Component-manifest timeout caps also follow the active provider owner. API-owned planning remains hard-capped at 120 seconds. Locally owned component generation may be configured up to 240 seconds with `CGNK_PROVIDER_COMPONENT_MANIFEST_TIMEOUT_CAP`, because bounded librarian prefill plus a multi-file documentation manifest can exceed the API-oriented transport window on local hardware. Both the manifest call and its enclosing component/semantic-attempt call use this same owner-aware cap; an outer API-oriented limit cannot silently truncate the local allowance. The overall run deadline and manifest validators remain authoritative.

The local-model transport applies the same ownership distinction at its final request boundary. Generation tasks may run for up to 240 seconds (optionally lowered with `CGNK_LOCAL_MODEL_REQUEST_TIMEOUT_CAP`), while public-reply and other non-generation tasks remain capped at 120 seconds. Component-file generation and locally owned semantic review default to 180 seconds and may be adjusted through `CGNK_PROVIDER_COMPONENT_FILE_TIMEOUT_CAP` and `CGNK_PROVIDER_SEMANTIC_REVIEW_TIMEOUT_CAP`; API-owned calls retain their 90-second caps. Manifest, leaf, review, outer-attempt, and transport layers resolve the active owner before applying a cap. No downstream layer may reapply an unconditional API-oriented 90- or 120-second clamp after the pipeline has granted a longer bounded local-generation timeout.

For a backend with a frozen stage graph, manifest normalization also supplies canonical dependency edges before the leaf work graph and librarian query are built. The application entrypoint depends on the orchestrator; the orchestrator depends on the stage facade and artifact store; persistence and preview depend on the story/asset domain; and bounded stage children depend only on the domain modules they consume. These edges determine generation order, exact interface feedforward, downstream repair closure, and allowed imports. Semantic similarity alone cannot substitute for a declared dependency.

The normalized backend entrypoint publishes `initialize_app`, imports the frozen stage facade, constructs `ProjectOrchestrator` with every required stage in declared order, and executes that nonempty real graph. The normalized orchestrator consumes plain stage callables through `stage(state)` with a structured `status`/`output` result and must inspect both result fields rather than treating any arbitrary mapping as success. Every assigned frozen pipeline-stage function accepts exactly one `state` mapping and every return path emits a result mapping whose status is `success` or `error` and whose output is itself a mapping; returning the mutable input state or a string payload is rejected. These AST rules run both on a newly generated leaf and on current manifest-aware component-cache validation, so historical syntax-only PASS cannot preserve an empty graph or incompatible stage protocol. Structured artifact-store cache validation likewise rejects missing frozen record fields and opaque `Dict[str, bytes]` storage. Orchestrator validation rejects `stage.execute(state)` object-method assumptions, fixture validation rejects a defined `run_fixture` that is never executed from a main guard, and foundation validation parses generated `pyproject.toml` as TOML before it can enter a checkpoint. Cached-component and assembled-project quality validation repeat that TOML parse so a stronger current contract invalidates a stale malformed foundation checkpoint even when it is upstream of the active repair leaf. Component reasoning repair remains on the existing Provider generation route but is a code task and therefore uses the configured code model rather than the general reasoning model. Post-build diagnostics recognize TOML paths and configuration-syntax failures as foundation targets instead of misrouting them to frontend files. Deterministic leaf contract mismatches are bounded repairable generation failures: their complete rejection history is returned to the responsible leaf model within the existing Provider route instead of terminating after the first structurally valid but contract-invalid candidate. During semantic repair, spec-hash mismatch may be ignored only for components strictly upstream of the earliest repair target. Downstream checkpoints must match the current feedforward interface hash, so an upstream interface change invalidates stale tests/media/docs instead of retaining component PASS from an obsolete API.

A same-run semantic repair plan always overwrites empty or stale compiled identity fields with the exact live user goal and component pipeline before the next attempt. This identity is evaluated before requesting any component manifest: validated components strictly upstream of the earliest repair target are reused directly, while the target and affected downstream closure remain eligible for regeneration. A blank legacy `raw_user_goal` cannot silently turn an affected-only media repair into nondeterministic backend manifest regeneration.

For a generated project with `demo/run_fixture.py`, required pipeline artifacts, or the background/sprite stage pair, candidate post-build must execute the generated fixture through the bounded Python command runner. It independently verifies command success, rejects a structured failure result printed by a zero-exit fixture, verifies every declared stage artifact as parseable object JSON with the declared fields, requires at least four decoder-valid distinct PNG hashes when visual generation is required, and requires at least two sprite PNGs with meaningful transparency. Generated fixture media is validated by role: backgrounds retain the 640x360 minimum used for reviewable scene media, while named sprite/character assets use a 256x256 minimum plus the transparency contract; the screenshot geometry threshold must not reject valid square sprites. Fixture failure blocks screenshot collection, candidate review readiness, and post-build PASS; support receipts cannot substitute for the required project files. The post-build repair compiler includes the structured fixture receipt in its failure log and routes fixture or stage-artifact failures first to `demo/run_fixture.py`, exact traceback-named stage leaves, and the real media/stage owners, never to an unrelated frontend leaf merely because screenshot collection was subsequently blocked. Ordinary repairs remain capped at three exact files; a multi-root fixture/media failure may carry at most five evidenced owner files so distinct stage and image-generation defects are not repeatedly hidden behind the same generic three-file prefix. Deterministic-only repair suppression applies only when no model-owned test, fixture, stage-artifact, media, or runtime failure is present; a simultaneous deterministic frontend symptom cannot erase the model repair actions for those independent root causes.

When a generated Python test is repaired after post-build failure, the repair payload must include bounded exact definitions for the local functions, classes, and constants imported by that test, following facade re-exports to their implementation leaves. This dependency context is authoritative: repaired tests must call the implemented signatures and validate the implemented public result shape instead of inventing compatibility fixtures, methods, or legacy interfaces.

Candidate UI smoke validation derives its domain identity keywords from the current `complexity_project_contract.json` selected project name and summary, compares them case-insensitively, and never applies a fixed sample-domain vocabulary to unrelated generated projects. If no selected-project contract vocabulary exists, title, body length, console, network, and image checks remain authoritative without manufacturing a domain-keyword failure.

Candidate post-build may reuse an existing workflow video only after the canonical video diagnostic confirms that the file is non-placeholder, large enough, and longer than one second. A later usage-planning pass that produces no new video must not erase earlier valid evidence. Static HTML usage inventory follows the local CSS and JavaScript paths actually declared by `index.html`, including `src/` layouts, instead of assuming root-level sample filenames.

For a selected project with four or more user-visible pipeline capabilities, browser evidence must prove a real workspace rather than a titled shell: at least sixty percent of the required capability groups must be visible, the page must expose a bounded minimum of semantic interactive controls, at least three workspace regions, and sufficient visible product text. Browser capture records these structural metrics and post-build cannot pass or request user review when the UI quality smoke fails. UI repair is routed together to the existing HTML, JavaScript, and CSS owners with bounded sibling feedforward context so visible capability, behavior, and styling contracts remain aligned.

The same UI acceptance contract is enforced before repaired frontend source is written: HTML must expose the required capability coverage, semantic controls, regions, and visible text; JavaScript must bind several concrete controls to observable behavior without placeholder simulations; CSS must provide a substantial responsive multi-region layout. UI diagnostics are isolated from already-passing test and fixture logs, and each provider call carries its exact target path so local model routing and evidence remain attributable.

A workspace region may use a semantic section/article/aside, an explicit region/tab panel role, or a clearly named `.section`, `.panel`, or `.workspace-region` container. Complex frontend repair still must preserve modular ownership: `index.html` loads `src/styles.css` and `src/app.js`, while non-empty inline style/script blocks and visible unimplemented/TODO behavior are rejected.

When a repaired complex `index.html` already declares the required external owners, the source boundary deterministically removes non-`src` inline script and style blocks before validation. This ownership normalization never creates labels, controls, regions, styling, or behavior; the provider must still supply those product-specific elements and both external owner leaves must independently pass their contracts.

Frontend repair payloads compile the failed capability groups into a small `ui_repair_brief` with required visible labels, three product-specific feature areas, and exact structural minima. A repair may not return the existing shell unchanged or satisfy feedback by appending comments/duplicate selectors; HTML, behavior, and styling must replace the shell coherently.

For a `ui_quality_failure`, each frontend repair leaf discards its old shell content and is regenerated only from the exact UI contract plus already-accepted sibling replacements. The old HTML/JavaScript/CSS siblings are not repeated as repair context, preventing small models from copying a minimal shell. JavaScript self-imports are rejected before any atomic write.

When a frontend replacement fails its source boundary, the next bounded retry receives the ownership-normalized rejected replacement, the current unresolved validation error, and a bounded diagnostic history. It repairs the new source in place and preserves already-satisfied UI behaviors instead of restarting from the older candidate shell. If two normalized replacements are identical, the final bounded retry discards the stagnant source and regenerates only that leaf from the same UI contract and accepted siblings. The project tree remains unchanged until the complete repair set passes atomically.

The run librarian may retrieve candidate-only rejected leaves from the same run as bounded repair memory. It revalidates each bounded candidate against the current contract and selects the one with the fewest current violations, using source size and recency only as tie-breakers, instead of trusting the newest file or a stale historical error. The evidence remains rejected until current per-leaf and cross-owner checks pass, and even then it cannot be written or promoted without the complete atomic repair set. For HTML identity failures, the repair brief derives an exact visible body identity line from the bounded domain vocabulary and states that document-title or attribute text does not satisfy it.

Source-boundary feedback must be executable rather than qualitative. In particular, CSS repair feedback reports the observed concrete-rule count and the exact minimum, identifies a missing responsive breakpoint, and names the accepted grid/flex layout declarations. The UI repair brief carries the same measurable thresholds so a bounded local model can close the gap without guessing or repeated comment-only edits.

Frontend source and browser acceptance use the same visible-body and workspace-region semantics: document-head text cannot satisfy body-content thresholds, and semantic region elements or explicit `.section`, `.panel`, and `.workspace-region` containers are counted consistently. The selected contract's bounded domain keywords are carried into repair prompts and evidence. Inline event attributes, `not implemented`/`implement logic` prose, sample empty-state comments, console logging used as product behavior, and export-only DOM mutations cannot satisfy modular JavaScript behavior.

Complex workspace review includes a design-system and cross-owner interface gate. HTML provides one visible product header, hierarchical feature headings, an observable status region, and capability-driven real media preview slots. JavaScript binds DOMContentLoaded to the document, resolves accepted HTML ids/actions, and exposes more than export-only DOM updates. CSS must style the exact accepted workspace owner, define and consume a bounded token system, provide responsive grid/flex layout, hierarchy, radius/elevation, and keyboard focus treatment. The rule threshold is deliberately small and semantic requirements carry the quality weight, so duplicate selectors cannot substitute for design. A structurally populated screenshot whose blank score exceeds 0.90 remains a UI quality failure and cannot authorize review or delivery.

Declaring design tokens is not sufficient: complex-workspace CSS must consume at least five distinct tokens across the page, header, surfaces, controls, spacing, radius, or type. The body must establish a page background and text color, the product header must have intentional spacing plus a surface/border/elevation treatment, and the base button—not only its hover state—must define a background and radius. A canvas preview must use at least two drawing operations including content-bearing text, image, or image-data rendering; a single solid rectangle is pixel activity but not meaningful preview evidence.

For a complex workspace with five or more semantic regions, layout declarations on an unused class do not count: the accepted workspace owner itself must define a real multi-column grid or wrapping flex layout, and responsive rules must change that owner rather than an orphan selector. A declared canvas preview is a drawing interface, not an HTML container. JavaScript must obtain its 2D context and perform visible drawing calls, or HTML must use a non-canvas preview surface; assigning canvas `innerHTML`/`textContent` cannot satisfy preview behavior. The bounded semantic adapter may retarget such an invalid canvas HTML write to an already-accepted output in the same region, but the cross-owner gate will still reject an undrawn canvas that remains declared.

For explicit repeated grid columns, the cross-owner gate estimates desktop region width from the accepted workspace owner's own `max-width`, column count, and gap, normalizing px/rem values. An estimated column below the 320px browser usability floor is rejected before atomic commit with actionable alternatives: widen the viewport-bounded owner, reduce the desktop column count, or use `minmax(320px, 1fr)`. An unused wide container or a numeric declaration on another selector cannot satisfy this interface.

Browser design diagnostics also measure horizontal overflow, control hit-target geometry, oversized media, empty feature regions, region width, the maximum number of workspace regions sharing a desktop row, blank canvas pixels, and visible status content. A five-or-more-region desktop workspace that still places at most one region per row, a majority of materially narrow regions, or an alpha-empty preview canvas is a UI quality failure. Capability-driven graph workspaces must show actual tree/node examples and preview-capable workspaces must expose a dedicated, visibly rendered preview surface. CSS must bound the workspace and media, use valid `calc(...)` arithmetic when needed, and set an explicit control minimum height. These geometry and content checks prevent giant raw images, empty cards, or a styled but functionally blank canvas from satisfying visual density alone.

Computed-style and canvas-detail diagnostics also reject a product header with no spacing/surface/border/elevation treatment, a majority of buttons retaining zero-radius browser-default styling, and a preview canvas with at most three sampled opaque colors after its action runs. These are intentionally conservative anti-default/anti-solid-block checks; they do not prescribe a palette or visual theme, but they prevent raw browser chrome and a single color rectangle from being promoted as designed evidence.

Before capturing visual evidence, the browser runner exercises the first declared preview action when one exists and records `preview_action_exercised`; blank-canvas diagnostics are measured after that interaction. This keeps source assurance and customer workflow control aligned: drawing code that is never reachable still fails, while a valid click-driven preview is judged after the real action rather than only at initial page load. CSS feedforward also exposes a 320px desktop region-width floor and at least two regions per desktop row for complex workspaces; these are measurable usability bounds, not a fixed visual theme.

When screenshot capture fails, the UI evidence status may be `skipped` or blocked, but the discovery-derived domain vocabulary and capability groups remain attached to `ui_smoke`. Outer repair iterations must therefore retain the same complex-workspace source and semantic-adapter contract; loss of visual evidence cannot silently disable UI ownership validation.

The bounded `ui_semantic_adapter` is part of the existing post-build repair lane, not a generation route. For a complex Provider-authored workspace it may convert a no-argument inline button handler into the equivalent `data-action` interface, restore declared external CSS/JavaScript owners, remove stale root-level duplicates or a competing legacy `src/main.js` owner when the accepted semantic workspace already declares `src/app.js`, remove the resulting orphaned empty root, close one unambiguous unterminated `<main>`, and add a stable id to an already-existing status interface. It must not create user-visible product content, sample graph nodes, capability buttons, result surfaces, status copy, business state, behavior, or visual styling. Missing product interfaces remain Provider repair failures. Accepted and rejected frontend leaf caches carry the current semantic-adapter policy version; records from an older policy are not eligible for reuse. Every applied action records `pipeline_fallback`, creates no delivery evidence, and remains subject to current per-file, cross-owner, browser, test, fixture, and atomic-set validation.

Blank-page, missing-entrypoint, missing-static-entry, and frontend/backend startup mismatch findings must repair the current project's evidenced HTML/JavaScript/CSS owners through the existing Provider route. Formal post-build repair must not synthesize or inject a fixed-domain demo page, sample business data, empty root shell, or competing frontend entrypoint. Old repair plans that still name those retired deterministic scaffold actions are rejected as legacy actions and cannot change candidate files.

Complex-workspace source assurance matches the browser evidence semantics before another expensive run. More than one semantic region may not consist only of a heading/button shell; regions need an input, list/node, output, media, or preview surface, and rejection feedback names the exact region ids/headings that remain empty. Duplicate DOM ids are rejected before JavaScript/CSS sibling generation. Cross-owner validation requires CSS selectors to cover at least sixty percent of accepted semantic regions (or a shared region selector), exact `data-action` bindings rather than unrelated DOM-id counts, and JavaScript rendering into an accepted preview surface. Blocking `prompt`/`alert` flows are rejected for complex workspaces because editing and feedback must remain in visible controls, status, and preview surfaces. These checks prevent syntactically rich but visually inert CSS/JavaScript from passing module validation.

The post-build UI repair brief derives its feature areas, action names, suggested region ids, and state-bearing HTML primitives from the current discovery capability groups. Generic behavior terms map to bounded interface shapes such as edit→label/input/list, bind→label/select/output, preview→output/canvas/media, and validate/export→visible output/status. This is model guidance inside the existing Provider lane, not generated business code: no VN, task-board, CS, or other sample-domain feature list may be hard-coded into the formal repair kernel.

An accepted HTML leaf publishes a bounded DOM action contract for sibling JavaScript: exact element types, action-to-region bindings, state-bearing ids, status ids, and preview ids. JavaScript may read `.value` only from form controls and may not replace a semantic region container to simulate an update. Every complex-workspace status surface has a stable id. Provider repair leaves that pass their current single-file and accepted-sibling boundaries are stored only as candidate-only `validated_pending_atomic_commit` artifacts. A later run must revalidate each staged leaf under the current contract and sibling set before reuse; staging never writes the generated project, bypasses atomic set application, or authorizes review/PASS.

The JavaScript repair payload narrows that DOM contract into an executable interface: an allowlist of ids and element types, one default status target, and per-action readable form ids plus writable output/list/media/status ids. Stagnation never discards a closer accepted-interface replacement merely because two outputs match; it retains that source and performs an interface-directed rewrite against the exact unresolved targets. The semantic adapter may close one unambiguous unterminated `<main>` owner before validation and records that fallback; structurally unbalanced workspace ownership cannot pass silently.

When Provider JavaScript already implements an action but overwrites an accepted semantic region container, the same bounded semantic-adapter lane may retarget only that result write to an already-existing `<output>` in the same region. A canvas HTML write may likewise move only to an already-existing output in that canvas region. References to invented or absent ids remain validation failures; they must never be collapsed into a generic status target. The adapter records `pipeline_fallback`; source, cross-owner, runtime, browser, and manual review gates still decide acceptance.

CSS/HTML selector coherence distinguishes a bare semantic tag selector from a similarly named class: `.section` cannot satisfy coverage for `<section>` without that class. At least sixty percent of accepted regions must receive real matching styles, and browser evidence independently counts regions with no background, border, or shadow hierarchy. Buttons and form controls must both meet the hit-target contract; a button-only `min-height` rule cannot hide undersized inputs or selects. Source and computed-browser gates use the same intended interaction and visual-hierarchy boundary.

The bounded CSS semantic adapter may retarget an existing `.section`, `.article`, or `.aside` selector to the same-named semantic tag only when accepted HTML has at least three regions all using that tag and has no element owning the class; declarations are preserved byte-for-byte apart from selector ownership. It cannot add hit-target rules or synthesize declarations, layout, palette, typography, visual hierarchy, media treatment, or responsive evidence. Missing accessibility or design requirements remain Provider repair failures and are independently validated. For a CSS repair leaf, the run librarian projects the currently accepted HTML into an exact `accepted_css_selector_contract`: workspace-owner selectors, per-region id/class/tag alternatives, minimum region coverage, shared semantic tag alternatives, the form-control selector, real visual-asset container/image selectors, required media properties, and preview-surface selectors. Repair feedback names uncovered accepted selectors. This is feedforward interface context for the same Provider repair turn, not generated styling and not a second repair route.

Repeated rejected frontend leaves use a language-specific stagnation escape contract. JavaScript receives only its accepted DOM action interface, CSS receives only the accepted selector contract, and HTML receives only the bounded semantic-region brief. A retry for one owner must never inherit another owner's repair instructions; in particular, CSS cannot be told to satisfy JavaScript DOM read/write rules. Stagnation context remains candidate-only repair feedback and cannot authorize a PASS.

The JavaScript interface includes a structured canvas preview contract derived from accepted HTML: exact canvas ids, a minimum of two drawing operations, allowed content-bearing operations, and the forbidden single-operation solid-fill case. Repeated JS output must repair against this structure rather than only receiving prose about visual quality.

For a repeated CSS desktop-width failure, the stagnation contract requires explicit arithmetic: workspace width must cover the region-width floor times the column count plus total gaps, or the model must reduce columns/use a matching `minmax(...)`. Returning the rejected `max-width`/column/gap tuple unchanged is a contract violation, not a new attempt.

The post-build frontend librarian removes duplicated sibling source text from a leaf prompt after the accepted atomic set has been projected into exact interfaces. The current leaf remains available once through `target_file_contents`; HTML keeps the bounded semantic brief, JavaScript keeps the DOM/action interface, and CSS keeps the selector contract. The `CGKNPostBuildFrontendLibrarianSlice` records which interface projections were retained and how many duplicate source characters were removed. Full accepted leaves remain in memory for independent cross-owner validation, so context slicing cannot weaken the atomic-set gate or authorize delivery.

Frontend repair feedback is monotonic. The repair loop assigns a validation distance that weights structural interface regressions—lost selector coverage, wrong owners, destructive DOM writes, nonexistent/duplicate ids, and missing region state—above bounded mechanical styling defects. It retains the closest rejected candidate as the next repair base and records when a later output regressed, while preserving the complete error history. “Latest” is therefore not treated as “best”; every retained candidate is revalidated and remains candidate-only until the whole atomic set passes.

When a closest rejected candidate is retained, the frontend librarian exposes it as the single `target_file_contents` repair base and marks it `candidate_only`; the older production leaf is not duplicated into that model turn. Rejected-replacement feedback stores only a reference to that field, never a second copy of the same source body. This prevents the model from restarting from an older leaf, preserves scarce local context for the actual repair contract, and leaves atomic validation and production writes unchanged.

If bounded semantic ownership normalization improves a rejected leaf but later validation still finds unrelated defects, the normalized candidate—not its pre-normalization source—becomes the next candidate-only repair base. Its remaining validation error and distance are recomputed; no normalized leaf is written to production before full per-file and atomic-set acceptance.

Post-build repair may mark a candidate review-ready only from the current complete acceptance state: tests pass, the generated-project fixture passes, UI smoke passes, and screenshot evidence exists or is explicitly environment-blocked. A passing historical attempt, a screenshot by itself, or passing tests with a failed UI cannot promote review readiness.

Each rejected post-build leaf is retained under the run's bounded `artifacts/post_build_rejections/` diagnostics with its validation error and candidate-only marker. Rejected source is evidence for repair feedback only, is never copied into the project or delivery package, and cannot authorize a PASS.

For a JavaScript workspace repair, accepted sibling HTML is reduced to an exact DOM-id allowlist and paired with concrete local behaviors derived from the selected capability groups: edit/render, validate, generate assets, bind, preview, JSON export, and local persistence. Source validation requires at least one concrete event entrypoint (which may implement delegation or a binding helper), visible DOM mutation, localStorage reload, and a real JSON download using either Blob/object URL or a JSON data URL; logging, TODO/placeholder comments, placeholder functions, or simulated actions do not satisfy the contract.

When the configured API owner is unavailable for a code-generation or code-repair task and the routing profile is not `api_only`, the existing provider route may make one bounded local-model fallback through the same output contract and validation chain. Covered availability failures are exhausted retryable transport errors, missing provider configuration, key-usage limits, forbidden access, and unsupported provider methods. It records a `pipeline_fallback` event with source, destination, task, and reason. The fallback does not change configured ownership, does not apply to public replies or arbitrary tasks, and cannot bypass atomic file validation or the formal delivery gate.

When fixture execution and pytest collection fail in the same post-build run, the exact traceback-named test leaf is prioritized immediately after the fixture and before inferred backend/media owners. The Provider repair request preserves the five-file allowance for these multi-root failures instead of silently truncating the compiled plan back to the ordinary three-file limit.

Post-build repair uses exact failure provenance before secondary missing-output symptoms. If the fixture traceback names `demo/run_fixture.py` itself, incomplete media counts and absent downstream stage artifacts caused by that early exit do not authorize speculative rewrites of image adapters, capture wrappers, orchestrators, or stages. Exact traceback-named tests and backend leaves remain independently actionable.

For component and post-build file-repair responses, a local model may omit a redundant top-level `component_id` when it already returns a non-empty `files` array. Bounded response normalization supplies the exact requested component id before contract validation; it never rewrites a conflicting id or expands file ownership. This prevents schema-only retries from exhausting otherwise valid local repair output.

## Local Project Team Layer

CGKN may maintain local conversation, active project, managed project, and revision-history state through `local_conversation_manager`, `local_repo_manager`, `main_agent_manager`, and `project_revision_lane`. These modules are coordination and history layers only. They do not create a second formal generation path.

Project revisions must preserve the previous active project until the new revision passes the reviewed provider route, post-build finalization, `local_packager`, factual checking, final adaptive judgment, and `delivery_manifest.json`. `NOT_EVALUATED` does not promote a revision to `current`; only a final allowed verdict may promote it. A failed revision records failure state and never replaces the current revision.

Model defaults must be selected through `model_policy` for provider generation and connectivity checks so different entrypoints do not silently test or run different default models.

Old `BLOCKED` and gate terminology must not be user-visible.

`backend_controls` are compatibility logs only, never execution queues.
