# ORBIT-360 项目愿景

## 一句话愿景

让 CGKN 在一个可重复、可观察、可局部修复的真实项目中证明：面对 ACFV 参考等级的 360 个依赖工作单元，系统仍能保持有界上下文、正确执行、可靠续跑和最小范围重算。

## 为什么需要它

小项目通过测试，并不能说明大型项目也可靠。规模扩大后，常见问题包括：

- 每个任务接收全部项目上下文，导致输入失控；
- 依赖关系不清晰，无法安全并行；
- 中途失败后从头重跑，浪费已经验证的结果；
- 修改一个单元却重新生成整个项目；
- 只统计文件数量，没有真实执行和可检查证据。

ORBIT-360 把这些风险变成一个可以本地运行的测试项目。

## 用户与使用场景

主要用户是维护 CGKN 生成、规划、检查点和修复机制的开发者。

典型场景：

1. 在本地生成 360 个有依赖关系的工作单元。
2. 验证分层执行结果和每个单元的内容哈希。
3. 再次运行，确认已验证结果被复用。
4. 修改指定单元，确认只失效它和传递下游。
5. 检查运行报告，区分执行完成与正式交付证据。

## 核心能力

- 默认 `360` 个工作单元、层宽 `35`，与仓库 ACFV reference scale 对齐。
- 每个单元拥有稳定 ID、层级、直接依赖、权重、修订号和自哈希。
- 物化阶段产生单元描述、接口注册表和边界校验收据。
- 执行阶段按依赖层并行，输出确定性结果和检查点。
- 续跑阶段重新校验单元、依赖结果和哈希，只复用仍然有效的结果。
- 修复阶段计算传递下游闭包，只删除闭包内的检查点结果。
- 所有运行输出都明确标记 `formal_evidence_status=NOT_EVALUATED`。

## 非目标

- 不替代 CGKN Provider 项目生成。
- 不成为 Telegram 生成主线或第二条交付路径。
- 不调用 `local_packager`，不生成交付 ZIP，不宣称正式 PASS。
- 不执行动态生成的 Python、Shell 或任意用户命令。
- 不模拟外部 API、图形界面或真实客户业务。

## 验收标准

1. 默认计划精确包含 360 个单元，层宽为 35。
2. 首次运行执行 360 个单元，边界收据与结果均可独立校验。
3. 第二次运行执行 0 个单元并复用 360 个有效结果。
4. 修复 `unit_008` 时，宽度 35 的传递闭包精确包含 11 个单元。
5. 修复后运行只执行 11 个单元，复用另外 349 个单元。
6. 篡改单元描述或结果哈希时，执行必须拒绝或重新计算，不能静默复用。
7. 完整 360 单元场景在普通本地开发环境中于有界时间内完成。
